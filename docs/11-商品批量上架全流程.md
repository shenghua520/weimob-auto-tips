# 11 · 商品批量上架全流程（素材 → 导入 → 图文详情 → 库存）

> 🟡 **本章接口均为自查接口**（非官方，随前端发版可能失效）。官方通道见 [WOS 开放平台](官方-01-WOS开放平台.md) / [iPaaS 私域网关](官方-02-iPaaS私域网关.md)。
>
> 实战背景：把 249 个商品（448 个 SKU、2,448 张原图）从旧站搬到微盟商城。
> 全程实测于 2026-10-27，下面每一条都是真跑出来的，不是推测。

---

## 0. 一句话流程

```text
图片规范化（750×750 自适应 / 长详情图切段）
  → 素材按「商品」建二级分组并上传（拿 CDN URL）
    → 商品导入（Excel 69 列，图片填素材 URL）
      → 图文详情（把切段的详情图写进 goodsDesc）
        → 库存（导入不带库存，后台「商品入库」或库存调整）
```

**顺序不能乱**：商品的图片列只能填「已在素材库里的 URL」，所以素材必须先传完。

## 1. 图片规范化（最容易忽视、也最影响观感的一步）

### 1.1 商品图片：750×750 白底自适应，**不要裁剪**

微盟商品图片建议尺寸 **750×750** 或 **750×1000**。实测源图尺寸极其混乱：

| 类型 | 张数 | 宽度范围 | 高度范围 |
|---|---|---|---|
| 主图 | 249 | 430–2000 | 430–2000 |
| 轮播图 | 1,215 | 430–2000 | 430–2000 |
| 详情图 | 536 | 287–2000 | 16–**16384** |
| SKU 图 | 448 | 430–2008 | 430–6087 |

尺寸不统一 + 直接裁剪 = 小程序里图片变形/主体被切。**正确做法是"自适应"**：
等比缩放到画布内，四周补白，图片内容一个像素都不切。

#### 光"缩到 750×750 不裁"还不够——要先想清楚容器

这是踩得最深的一个坑。把图做成 750×750 方图上传后，前台照样显示成"球被切掉上下"。
原因不在图，在**容器**：

同一张 `defaultImageUrl` 会被前台多个位置复用，每个位置容器比例都不同、且都是
**裁切填充（cover/fill）**，不会给你补白：

| 位置 | 容器比例（实测，390 宽手机） |
|---|---|
| 商品详情页轮播 | 390×586 = **2:3** |
| 列表卡片 | 接近 **1:1** |
| 各种活动位 | 3:4 / 16:9 都有 |

一张 1:1 的图塞进 2:3 容器 → 上下被切；塞进 16:9 → 上下切得更狠。
你在 H5 上换设备看不出毛病（H5 容器会跟着图走），**小程序容器是固定的**，一换就露馅。

#### 解法：画布按最大需求给，主体收进"任何裁切都不碰"的安全区

**画布 750×1000（官方建议的 3:4），主体等比缩到中心 750×750 安全区，上下各补 125 白边。**

```js
// 1) 主体先放进 750×750 安全区
const body = await sharp(src)
  .resize({ width: 750, height: 750, fit: 'contain', background: { r: 255, g: 255, b: 255, alpha: 1 } })
  .flatten({ background: '#ffffff' })
  .toBuffer();

// 2) 扩到 750×1000 画布，上下各 125 白边
await sharp(body)
  .extend({ top: 125, bottom: 125, left: 0, right: 0, background: { r: 255, g: 255, b: 255, alpha: 1 } })
  .jpeg({ quality: 90, mozjpeg: true })
  .toFile(dst);
```

为什么这样能通吃：

| 容器 | 裁切方向 | 结果 |
|---|---|---|
| 3:4（750×1000） | 不裁 | 完整显示，含上下留白 |
| 1:1 | 裁上下各 125 | **正好裁在留白上，主体一个像素不碰** |
| 2:3 | 裁左右各 ~62 | 主体本身在白底内没贴边，仍完整 |

> 一句话记法：**画布往高的做，主体往中间收**。
> `fit:'contain'` 是补白（保留完整图），`fit:'cover'` 是裁切（会切边）——批量搬商品只能用 contain。

### 1.2 详情图：长图必须切段

源站详情图最长 **16,384px**（米面油品的米，常见 790×13,500）。这种图在微盟：

- 上传环节容易被压缩或直接失败；
- 就算传上去，小程序里也必须整张下载，首屏极慢；
- 商城详情区宽度固定 750，宽度不是 750 的图还会被二次缩放糊掉。

**做法**：宽度统一缩到 750，再按高度**均匀切分**，每段 ≤1200px，顺序命名。

```js
const buf = await sharp(src).resize({ width: 750 }).toBuffer();
const m = await sharp(buf).metadata();
const n = Math.max(1, Math.ceil(m.height / 1200));   // 段数
const segH = Math.ceil(m.height / n);                 // 均匀分段，避免最后一段只剩几像素
for (let y = 0, i = 1; y < m.height; y += segH, i++) {
  await sharp(buf)
    .extract({ left: 0, top: y, width: m.width, height: Math.min(segH, m.height - y) })
    .jpeg({ quality: 90 })
    .toFile(`${base}-${String(i).padStart(2, '0')}.jpg`);
}
```

⚠️ **不要用固定步长切**（`y += 1200`）：最后会剩一条几十像素的碎片，视觉上像图片被截断。
用 `Math.ceil(h / n)` 均匀分段，每段高度接近、首尾完整。

实测效果：一张 790×13,500 的米详情图 → 750 宽 × 11 段，每段约 1,160px。

### 1.3 命名要能"看得出顺序"

```text
G01.jpg G02.jpg …     商品图（G01 = 主图，G02 起为轮播）
S01.jpg S02.jpg …     SKU 图（对应规格）
D01-01.jpg D01-02.jpg 详情图第 1 张的第 1/2 段
```

导入商品时，图片列按 `G01 → G02 → …` 顺序拼成 URL 列表，顺序就是前台展示顺序。

### 1.4 源图可能损坏

批量处理 2,448 张，必有一两张 JPEG 是残缺的（下载中断）。报错长这样：

```text
Error: VipsJpeg: premature end of JPEG image
```

**必须逐文件 try/catch**，否则一张坏图会让整批中断（实测就是这样崩的）。
坏图记进 `坏图.json`，单独找源站重下。

## 2. 素材上传：三个接口 + COS 直传

### 2.1 完整链路

```text
POST /api3/mpmedia/center/upload/preUpload        → 拿到 COS 临时密钥 + saveKey
PUT  COS（bucket.region.myqcloud.com/saveKey）    → 上传二进制（用官方 SDK 签名）
POST /api3/mpmedia/center/upload/confirmUpload    → 拿到 CDN URL
POST /api3/material/center/material/insertMaterial → 入库到指定分组
```

### 2.2 请求头：两个接口的鉴权头**不一样**

这是最容易卡住的地方，头不对就报 `11010000002 参数错误`（误导性极强）。

| 接口 | 必需的业务头 |
|---|---|
| `mpmedia/center/upload/preUpload`<br>`mpmedia/center/upload/confirmUpload` | `bizkey: mp_material_center_upload`<br>`bizmaterialtype: 1`<br>`bizmaterialvid: 0`<br>`accesskey: ''`<br>**不要带 `apiclient`** |
| `material/center/material/insertMaterial` | `apiclient: saas-pc`<br>（不带 bizkey） |

公共头仍是 `authorization` + `weibom-bosid` + Cookie。

### 2.3 preUpload 请求体

```jsonc
{
  "contentType": "image/jpeg",
  "fileCode": "<文件前 64 字节的 hex>",     // 不是全文！就前 64 字节
  "fileMd5": "<整个文件的 md5>",
  "fileSize": 139009,
  "srcFileName": "主图.jpg",
  "requireType": "IMAGE",
  "riskReq": { "accountType": 15, "uid": <bosId> },
  "basicInfo": { /* 骨架 */ },
  "i18n": { "language": "zh-CN", "timezone": 8 },
  "extendInfo": { "refer": "/bos/products/mpmaterial/{bosId}/{key}/store/material", "source": 80 }
}
```

返回：

```jsonc
{
  "data": {
    "preProcessInfo": { "saveKey": "ol-6NoGC/xxxx.jpg", "mediaType": "IMAGE", "mediaTypeId": 160 },
    "cosTempInfo": { "secretId": "...", "secretKey": "...", "sessionToken": "...",
                     "region": "ap-shanghai", "bucket": "picserver-1252328573", "expire": 1793091234 },
    "continue": true     // false 表示秒传（服务端已有同 md5，跳过上传）
  }
}
```

### 2.4 COS 上传不要自己算签名

`cosTempInfo` 是临时密钥（带 `sessionToken`）。手工拼 `q-sign-algorithm=sha1` 极易踩
`SignatureDoesNotMatch`（实测手写签名失败）。直接用官方 SDK：

```js
const COS = require('cos-nodejs-sdk-v5');
const cos = new COS({ SecretId: cosTempInfo.secretId, SecretKey: cosTempInfo.secretKey, SecurityToken: cosTempInfo.sessionToken });
await new Promise((res, rej) => cos.putObject({
  Bucket: cosTempInfo.bucket, Region: cosTempInfo.region, Key: saveKey, Body: buf, ContentType: 'image/jpeg',
}, (e, d) => e ? rej(e) : res(d)));
```

前端页面走的是**分片上传**（InitiateMultipartUpload + PUT part + Complete），
但单次 `putObject` 完全可行，一张 8MB 的图也没问题。

### 2.5 insertMaterial：分组在这一步决定

```jsonc
{
  "url": "https://image-c.weimobwmc.com/ol-6NoGC/xxx.jpg",
  "groupId": 45308,          // ← 素材分组 ID
  "size": 139009,
  "title": "2640_G01.jpg",
  "materialType": 1,
  "materialFileType": 4,     // 4=jpg / 2=png
  "createUid": 12103830397,
  "orderInfo": { "order": 0, "stage": "stage_" + Date.now(), "total": 1 },
  "materialDetailExts": [],  // 可传 width/height
  "basicInfo": { /* 骨架 */ }
}
```

实测速度：**约 0.1~0.5 秒/张**（预签名是本地调用，COS 上传走并发）。3,844 张实测 10 分钟内跑完。

### 2.6 素材容量是账号级配额，跟图片大小无关

批量跑到一半会撞上这个：

```jsonc
{ "errcode": 11010000006, "errmsg": "素材容量已超出限额，请购买存储空间" }
```

排查过程（结论反直觉）：

| 线索 | 结果 |
|---|---|
| 素材页顶部文案 | 「总容量使用：**0%**」——看着根本没满 |
| `material/center/material/getMaterialTotal` | `{ capacity: 1536000, count: 824 }`（图片 385 / 全类型 824） |
| 把 `size` 字段改成 `1` 重传 | **报一模一样的错** → 与单张图大小无关 |
| 结论 | 是**账号套餐的素材配额**（条数/空间），不是累加溢出；页面那个 0% 不可信 |

**处理方式：URL 拿到了就是拿到了。**

`confirmUpload` 返回的 `url` 是 COS 上的真实地址，**商品导入和图文详情只认 URL，不认素材库记录**。
所以批量阶段直接加 `--noinsert` 跳过入库，URL 照收，商品上架完全不受影响。

配额扩容后，用 `scripts/16-mat-insert.js` 一键补登——它读 `素材未入库.json`
（每行记了 srcId / 文件名 / url / size / 分组 ID），只调 `insertMaterial` 不再重新上传，
所以补登很快，且支持断点续跑（已入库的写进 `素材已入库.json`，重跑自动跳过）：

```bash
node scripts/16-mat-insert.js --c=3     # 3,826 张约几分钟
```

> 顺带一个省时间的点：COS 是**秒传**——同 MD5 的文件再传一次，`preUpload` 会返回 `continue:false`，
> 直接跳过 `putObject`。所以脚本中断后续跑，18 张图只花 4 秒，不会重复占用空间。

### 2.7 ⚠️ 「素材容量已超出限额」的真凶：productInstanceId 错了一位

这一坑卡了整整一轮（3,826 张图全部入库失败），必须单独记。

**最坑的地方：报错完全误导。** 容量其实一直是够的，账号也没问题——
是请求体里一个字段写错，后端拿这个 ID 去查**素材额度**，查到的那条额度是 **0**，于是报超限。

真实值 vs 我当时写的：

| 字段 | 正确值 | 我写的 | 结果 |
|---|---|---|---|
| `productInstanceId`（顶层） | `24343333397` | `24343313397` | ❌ 容量超限 |
| `sourceProductInstanceId`（顶层） | `24343333397` | `24343313397` | ❌ 同上 |

#### 这两个 ID 到底是谁的？（重要，别自己吓自己）

同一商户下**有多个产品实例**，两个 ID 都是本商户的，不是别人的账号：

| | `24343333397` ✅ | `24343313397` ❌ |
|---|---|---|
| bosId（商户） | 4022657115397 | 4022657115397（**同一个**） |
| 归属 | 「商城」实例 | 同商户另一条产品线实例 |
| productId / versionId | 1 / 110499 | 145 / 112519 |
| `getMaterialTotal` 返回 | capacity **1536000**、count 439 | capacity **0**、count 439（同一份数据！） |

关键证据：两个 ID 查出来的 `count` **完全相同**（同一份素材数据），只有 `capacity` 一个 1536000、一个 0。
所以数据从没串号，只是拿着一个"额度为 0 的实例"去请求，必然被判超限。

账目也能对上：原有 385 张 + 补登 3,826 + 新主图 1,462 + 测试 6 = **5,679**，
与素材库 `totalCount` 一致，全在本账号。

> 为什么会搞混：这个商户的商品/库存走 productId **145** 那条线（basicInfo 里 productInstanceId 是 24343313397），
> 而素材/小程序走 productId **1**（24343333397）。**同一个 bosId 下两套实例，各自的 basicInfo 不一样**，
> 照抄商品模块的 basicInfo 去调素材接口就会踩这个坑。

**定位过程（可复用）**：先在界面上手动传一张图 → 抓真实 `insertMaterial` 请求 →
和脚本 body 逐字段 diff → 差异就出来了。别信错误文案，信 diff。

顺便，下面两个也一起补齐，虽然单独都不致命：

| 项 | 要求 |
|---|---|
| `user-agent` | 必须带，缺了会被风控拦（同样报容量超限，更难查） |
| `extendInfo` | `{ refer: '/bos/products/mpmaterial/{bosId}/{key}/store/material', source: 80 }` |

**验证结果**：改对之后，3,826 张素材补登 **91 秒全过、0 失败**（并发 4）。

### 2.8 最稳的做法：拿「界面真实请求体」当模板

手写 body 永远可能漏字段。可靠做法是把界面上成功过的那次请求存成模板，
每次只替换 `url / size / title / groupId`，其余字段一个不动：

```js
const PROTO = JSON.parse(抓到的真实请求体);
const body = { ...PROTO, url: u, size: sz, title: t, groupId: gid,
  orderInfo: { order: 0, stage: 'stage_' + Date.now(), total: 1 } };
```

图片和视频都用这招，一次成。

## 3. 素材分组：按商品归档

### 3.1 建组参数

```text
POST /api3/material/center/group/createGroup
{ ...base, name, level, parentId, sceneId: "default", createUid: 12103830397 }
```

| 层级 | level | parentId |
|---|---|---|
| 一级（顶层） | `0` | `-1` |
| 二级 | `1` | 一级分组的 `groupId` |

> 以前踩过：只传 `name` 会默认建成**一级**分组（parentId=0），不是二级。

### 3.2 命名规则：短名 + 唯一标识

批量搬家时素材文件名高度重复（每个商品都有"主图.jpg""轮播图3.jpg"），只按一级分类建组会导致
一个分组里几百张同名图，根本没法用。

**规则：`商品短名_商品ID`**，挂在对应一级分类下：

```text
米面油品 (45302)
├── 鲁花厨中香浓香菜籽油1.8L_2640
├── 五常稻花香2号大米真空袋装5_2893
└── …
学习文具 (45295)
├── 晨光洞洞笔hb铅笔小学生一二_3021
└── …
```

短名提取要点：

- 去掉 `【】()（）《》` 等壳子；
- 截断到 14 字（太长的商品名在左侧树里显示不下）；
- **敏感词先替换**——微盟分组名有内容校验，实测：

```text
errcode 11010300004  "名字包含敏感内容!【子弹】涉嫌【违禁】"
```

  把 `子弹 → 弹头`、`枪 → Q`、`刀 → D`、`毒 → D` 提前处理掉，避免 249 个里有一个失败。

### 3.3 幂等

建组前先 `getGroupList` 拉全树，已有同名（或映射表里已有 `srcId`）就跳过。
实测 249 个商品：新建 248、跳过 1、失败 0（敏感词那个替换后补建成功）。

### 3.4 视频：分组是独立的，靠 `materialType=3` 区分

图片和视频**不共用一套分组**。`getGroupList` / `createGroup` 都带 `materialType`：

| 类型 | materialType |
|---|---|
| 图片 | `1` |
| 视频 | `3` |

所以建视频分组 = 把图片那套请求体里的 `materialType` 改成 3 再发一次：

```js
// 9 个一级大类，level:0 + parentId:-1
await post('material/center/group/createGroup',
  { ...groupBaseWithMaterialType3, name: '学习文具', level: 0, parentId: -1,
    sceneId: 'default', createUid: 12103830397 });
```

> 视频分组**不需要按商品建二级**——11 个视频分到 9 个大类组里就够了，
> 跟图片那种「一商品一组」的粒度完全不同。

### 3.5 视频上传：比图片多三个字段

链路仍是 preUpload → COS → confirmUpload → insertMaterial，差异点：

| 环节 | 图片 | 视频 |
|---|---|---|
| `preUpload.requireType` | `IMAGE` | `VIDEO` |
| `preUpload.optionals` | 无 | `["SAVE_DURATION","SAVE_COVER"]`（不加就不返回时长/封面） |
| 上传头 `bizmaterialtype` | `1` | `3` |
| `insertMaterial.materialType` | `1` | `3` |
| `insertMaterial.materialFileType` | `4`（jpg） | `10`（mp4） |
| `insertMaterial.duration` | 无 | `confirmUpload` 返回的 `detail.duration`（秒） |
| `insertMaterial.materialDetailExts` | width/height | `thumb_url` / `thumb_width` / `thumb_height`（取 `detail.mediaCover`） |

实测 11 个视频（约 38MB）全部一次过，上传完落在对应大类分组里。

### 3.6 把视频挂到商品上

`mall/goods/update` 里两个字段，都是字符串：

```jsonc
{
  "goodsVideoUrl": "https://c.weimobwmc.com/ol-6NoGC/xxx.mp4",
  "goodsVideoImageUrl": "https://image-c.weimobwmc.com/ol-6NoGC/xxx.jpg"  // 封面，务必一起给
}
```

验证方式：手机端商品页首屏应出现**播放按钮**，右下角媒体计数从 `1/7` 变成 `1/8`（视频算第 1 个）。
只给 `goodsVideoUrl` 不给封面，前端会出现黑块，别省。

## 4. 商品导入：Excel 是唯一的批量入口

### 4.1 入口与接口

页面：商品列表 →「导入商品」→「单个销售」→ 下载模版 / 上传 → 立即导入。

```text
POST /api3/merchant/backstage/service/upload/preUpload     # 通用文件上传（同素材，但 bizeky 不同）
PUT  COS
POST /api3/merchant/backstage/service/upload/confirmUpload
POST /api3/mall/goods/import/importRetailMerchantGoodsAndItem
     { solutionType: 2, subGoodsTypes: [101,202,203,206,207], fileUrl, ... }
     → { data: { asyncProcessResult: { resultId: 9278593 } } }
```

**导入是异步的**，`resultId` 是查结果的钥匙。

### 4.2 查结果 / 下载失败明细（关键接口）

```text
POST /api3/merchant/backstage/service/download/detail
{ ..., "id": <resultId> }
→ data.excelResult = { totalCount, successCount, failCount }
   data.mediaUrl    = "https://c.weimobwmc.com/xxx.xlsx"   ← 失败明细 Excel
```

失败明细里有一列 **「失败原因」**，写得很直白，直接照着改就行。这是整套流程里最有用的调试入口。

> ⚠️ 别在页面上点「下载失败数据」——实测点击后页面直接崩溃（`Target page, context or browser has been closed`）。
> 走 `download/detail` 拿 `mediaUrl` 自己下载，稳得多。

### 4.3 模版 69 列，真正必填的只有 12 列

按报错一个个试出来的**最小可用字段集**：

| 列名 | 值 | 备注 |
|---|---|---|
| 商品序号 | 1,2,3… | 同商品多 SKU 用**同一个序号**，且不能与其他商品交错 |
| 商品类型 | `实物商品（物流发货）` | |
| 商品名称 | | **≤60 字符**，超了整行导入失败（见 4.4 坑 7） |
| 商品图片 | `url1;url2;url3` | **分号分隔**，见 4.4 |
| 可售状态 | `可售` | |
| 销售渠道 | `线上` | 不填报「销售渠道不能为空」 |
| 一级类目 / 二级类目 | 如 `食品` / `粮油干货` | 不填报「类目信息不能为空」 |
| 规格名称 / 规格值组合 | 如 `规格` / `1.8L` | **每个商品都要填，包括单规格**——不填会导进一个没有 SKU 的空壳商品，见 4.4 坑 6 |
| 商家统一价 | | |
| 商品分组 | `一级:二级`，如 `米面油品:菜籽油` | 分组必须先在系统里存在 |
| 配送方式 | `商家配送` | 不填报「配送方式不能为空」 |
| 商家配送模板 | 运费模板 ID | 不填报「商家配送模板不能为空」 |
| 支付方式 | `支持线上支付` | 不填报「支付方式不能为空」 |

其余（品牌、参数、属性、重量、标签、发票、服务…）**全部留空即可**，系统按默认值处理。

### 4.4 七个坑，每个都真实踩过

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | **多图分隔符** | 用逗号 `,` 时整串被当成一个 URL，商品主图 404 | 必须用**分号 `;`**（和"规格名称""属性"等多值字段一致） |
| 2 | **「一级分类」不能填** | 填「未分类」报「商品一级分类信息和后台需要保持一致」 | **整列留空**，分类只通过「商品分组」列表达 |
| 3 | **类目要先建** | 商户没建过类目时，类目接口返回空数组 | 用 `mall/goods/category/queryCategoryListForManagement` 递归取树，按真实品类映射 |
| 4 | **库存不在模版里** | 模版 69 列**没有库存数量列** | 见第 6 节，库存要单独做 |
| 5 | **同名商品会叠加** | 反复导入测试会生成多个同名商品 | 测试前先删，别靠肉眼认 |
| 6 | **单规格商品不填规格 → 没有 SKU** | 导入结果显示「成功 1 / 失败 0」，图片也正确，但商品详情里 `isMultiSku=false`、`skuList=null`，商品上架后根本卖不了 | **不管几个规格都写「规格名称 + 规格值组合」**；单规格就写 `规格 / 1.8L`。补上后 `isMultiSku=true`、`specInfoList` 有值 |
| 7 | **商品名称超 60 字符** | 报「商品名称有误-商品名称超过限制」，且**同一商品的其它 SKU 行会连带报**「同一商品的其他规格信息有误」 | 生成 Excel 时就截断到 58 字符。那种 `A/B/C/D 中文名` 的货号式命名最容易超——249 个里中了 6 个 |

### 4.5 类目：先递归取树，再按品类映射

```text
POST /api3/mall/goods/category/queryCategoryListForManagement
{ "parentCategoryId": 0, ... }        # 递归子级，实测只有 2 层（27 个一级 / 216 个二级）
```

另一个有用的接口是**商户已用类目**（说明这些类目资质已通过，导入不会卡资质）：

```text
POST /api3/mall/goods/category/queryMerchantUsedCategoryList
→ [ { usedCategoryId: 231, categoryTreeTitle: ["其他","其他"] }, ... ]
```

文具/体育/粮油这套映射就是据此定的：

| 商品类型 | 一级类目 | 二级类目 | ID |
|---|---|---|---|
| 铅笔/中性笔/笔芯/橡皮/尺规/本册/修正带/马克笔 | 3C数码 | 文具耗材 | 8 / 89 |
| 羽毛球/跳绳/足球/篮球 | 服饰 | 运动户外 | 3 / 47 |
| 菜籽油/亚麻籽油/大米 | 食品 | 粮油干货 | 1 / 31 |

## 5. 图文详情：详情图不进「商品图片」

### 5.1 分清楚两个位置

| 位置 | 字段 | 内容 |
|---|---|---|
| 商品图片（第 1 张是主图） | `goodsImageUrl[]` | 主图 + 轮播图，前端按顺序轮播 |
| **图文详情** | `goodsDesc` | 详情长图，详情区整段展示 |

导入模版**只有「商品图片」一列，没有图文详情字段**。所以详情图只能在导入后用
`mall/goods/update` 写进 `goodsDesc`。

### 5.2 update 请求体：拿「保存过的 payload」当骨架

`mall/goods/update` 要求**完整对象**，少字段就报错（实测 `skuList 为空`、`categoryId 为空`）。
最省事的做法是：

1. 在页面上对任意商品点一次「保存」，把请求体存下来当模板；
2. 之后每个商品：用 `queryGoodsDetail` 覆盖关键字段 + 设置 `goodsDesc`。

```js
const body = {
  ...template,                    // 保存成功过的完整 payload
  ...detail,                      // 当前商品详情
  goodsId, solutionType: 2,
  categoryId: catList.at(-1).categoryId,     // 必填！取类目树最后一级
  goodsClassifyIdList: goodsClassifyList.map(c => c.classifyId),  // 必填！
  goodsImageUrl: [...main, ...banner],
  defaultImageUrl: main[0],
  goodsDesc: detailImgs.map(u => `<p style="text-align:center"><img src="${u}" style="max-width:100%"/></p>`).join(''),
};
await post('mall/goods/update', body);
```

### 5.3 queryGoodsDetail 必须带 filterOption

不带这串开关，返回的 `skuList`、`goodsClassifyList` 全是空：

```jsonc
{
  "basicInfo": {...}, "solutionType": 2, "goodsId": "161453658100397",   // 注意是字符串
  "filterOption": {
    "isQuerySkuInfo": true, "isQueryClassifyInfo": true, "isQueryCategoryInfo": true,
    "isQueryDescInfo": true, "isQueryPicInfo": true, "isQuerySaleInfo": true,
    "isQueryGoodsPriceInfo": true, "isQueryGoodsStockInfo": true,
    "isQueryPropertyInfo": true, "isQueryBrandInfo": true, "isQueryTagInfo": true,
    "isQueryGoodsLimit": true, "isQueryInvoiceConfig": true, "isQueryAttachInfo": true,
    "isQueryAutoSell": true, "isQueryAutoOffline": true, "isQueryVideoInfo": true,
    "isQueryAppointmentTimeInfo": true, "isQueryGoodsAbilitiesDetailInfo": true,
    "querySelfPickupSiteShip": true, "isFilterDeleted": true, "queryVidBizType": true
    /* 其余每项都写 true 最保险 */
  },
  "i18n": {...}, "extendInfo": {...}
}
```

### 5.4 goodsDesc 用什么格式

`goodsDesc` 是 **HTML 字符串**（未设置时为 `null`）。一段 `<p><img/></p>` 即可，
每张切段图一段，顺序即展示顺序：

```html
<p style="text-align:center"><img src="https://.../D01-01.jpg" style="max-width:100%" /></p>
<p style="text-align:center"><img src="https://.../D01-02.jpg" style="max-width:100%" /></p>
```

写完后回读 `goodsDesc` 长度验证（实测 6 张详情图 870 字符，编辑器里正常显示）。

### 5.5 详情图"只显示一部分"：小程序不认 max-width

H5 里 `<img style="max-width:100%">` 是好的，但小程序的 `rich-text` 组件对 CSS 支持有限，
`max-width` 常常不生效，图片按原始宽度（750px）铺出来，超屏部分被容器裁掉——
**表现就是"详情只显示半截，点开图片却是完整的"**。

必须显式给宽高：

```html
<p style="margin:0;padding:0;text-align:center">
  <img src="..." style="width:100%;max-width:100%;height:auto;display:block;border:0"/>
</p>
```

要点：

- `width:100%` 才是让小程序生效的那一条，`max-width` 只能兜底；
- `height:auto` 保住比例，不然会压扁；
- `display:block` + 去掉 `<p>` 的默认边距，避免图之间出现白缝；
- 图片本身统一 **750 宽**（详情切段每段 ≤1200 高），任何屏宽下都是等比缩放，不需要留 2 倍图。

自查办法：手机上打开商品详情，**长按/点开某张详情图**——如果点开的图和页面里显示的不一致，
就是被裁了，回到上面查样式。

### 5.6 商品名超 60 字符：用副标题兜住

名称被截断很难看（`…MG KIDS食品级软头` 戛然而止）。微盟有 `subTitle` 字段，正好接上：

| 字段 | 放什么 |
|---|---|
| `title` | 前 58 字符 |
| `subTitle` | 第 58 字符之后的剩余部分（去掉开头空格/斜杠） |

实测效果：

```text
title    : ZCPN0383/ZCPN0384/ZCPN0385/ZCPN0386/ ZCPN0387 MG KIDS食品级软头
subTitle : 12/18/24/36/48 色水彩笔彩色笔绘画笔
```

前台连起来读就是完整商品名，既不丢信息也不触发长度校验。

### 5.7 别被 `skuList: null` 骗了

`queryGoodsDetail` 对**任何一个商品**返回的 `skuList` 都是 `null`——包括商户自己手工建的、
正在正常售卖的老商品。我一开始拿它当验收标准，白白排查了一轮。

**正确的验收口径：**

| 字段 | 含义 |
|---|---|
| `isMultiSku: true` + `specInfoList` 有值 | 规格已建立 → SKU 是有的 ✅ |
| `isMultiSku: false` 且 `specInfoList: null` | 真的没有 SKU（多半是导入时没填规格）❌ |

另一个能拿到真 SKU 的地方是 **`mall/goods/update` 的返回体**，里面 `data.skuList[0].skuId` 是实打实的。

## 6. 库存：导入真的不管

### 6.1 微盟的库存是独立模块

- **导入模版没有库存列**（69 列里只有「库存单位」，没有数量）；
- **批量修改**支持的字段列表里也没有库存（只有"库存扣减方式"）；
- 商品编辑页的「销售信息」里也没有库存输入框。

库存只能走 **库存管理 → 库存调整 / 商品入库**。

### 6.2 库存调整接口

```text
POST /api3/mall/mgr/stock/createAsyncStockTask
{
  "solutionType": 2,
  "assignType": 1,              // 1 = 覆盖更新   2 = 增量更新
  "stockNum": 1000,             // 覆盖时是目标值；增量时是变化量（可为负）
  "storeIdList": [],
  "itemSkuIdList": [312088241100397],
  "basicInfo": {...}
}
→ { data: { result: true, taskId: 3375674097 } }   // 异步任务
```

**参数语义实测**（和直觉相反，文档没写）：

| assignType | 语义 | 备注 |
|---|---|---|
| `1` | **覆盖更新** | 传负数报「分配库存覆盖更新库存数量不能是负数」 |
| `2` | **增量更新** | 正数加、负数减 |

### 6.3 三个坑

| 坑 | 表现 | 说明 |
|---|---|---|
| **只能加不能减** | 库存 3000，提交增量 -2000 或覆盖 1000，接口都返回 `result:true`，但库存不动 | 减库存要走出库/售后链路，手工减被静默忽略 |
| **异步延迟** | 提交后立刻回读是旧值 | 等 10–30 秒再查 |
| **读错字段** | 库存行有嵌套的 `storeWarehouse.totalStockNum`，顶层 `totalStockNum` 为 `null` | 要读 `storeWarehouse.totalStockNum` |

### 6.4 新商品没有仓库库存记录

导入出来的商品，库存行长这样：

```jsonc
{ "itemSkuId": 312088241100397, "specDetail": null,
  "storeWarehouse": { "warehouseId": null, "totalStockNum": 0 } }
```

而早先发的老商品有 `warehouseId: 306854216`。也就是说新 SKU 没绑定仓库。

**但别急着下"落不到账"的结论——任务只是慢。**

我第一次提交 448 个任务，等 15 秒回查全是 0，就以为失败了。实际上
`createAsyncStockTask` 是异步批处理，**要 1~3 分钟才落账**。多等一会儿再看，
418 个 SKU 已经是目标值了。

所以最省事的路径其实是 API 直调，不用碰入库单：

```jsonc
POST /api3/mall/mgr/stock/createAsyncStockTask
{
  "basicInfo": {...}, "solutionType": 2,
  "assignType": 1,          // 1=覆盖（可增可减）  2=增量（只能加）
  "stockNum": 100,
  "storeIdList": [],        // 新 SKU 没有仓库，留空即可
  "itemSkuIdList": [312098569100397],
  "extendInfo": { "refer": "/bos/products/ecGoods/{bosId}/{key}/stock/stock-adjustment", "source": 80 }
}
```

**验证节奏**：提交完先干别的，**至少等 3 分钟**再回查，别用 15 秒判定失败。
回查读 `pageList[].storeWarehouse.totalStockNum`（不是顶层字段）。

> 入库单那条路（后台「库存管理 → 入库单 → 商品入库」）也试过，两个坑：
> ① Excel 模板要 6 列（`商品名称/规格条码/规格/库存单位/商品创建来源/出入库数量`），
> 但**导入后表单里不显示数据**，弹窗只说"共导入 N 个"，成功与否看下一句文案；
> ② 就算导入成功，它也是**增量**——你想要的"统一 100"会变成"原值+100"，
> 反而要再覆盖一次。除非业务上确实要做入库流水，否则别绕这条路。

## 8. 这次踩坑清单（按疼痛程度排序）

1. **素材上传报「参数错误」** → 其实缺 `bizkey` 头，不是参数问题。
2. **商品图片多图不生效** → 分隔符必须是 `;`，逗号会被整串当一个 URL。
3. **「一级分类」填了反而失败** → 整列留空。
4. **`queryGoodsDetail` 返回空 skuList** → 缺 `filterOption` 一堆 true。
5. **单规格商品不填规格，导进去是个空壳** → 导入报"成功"，图也对，但 `isMultiSku=false`、没有 SKU，
   商品根本卖不了。**每个商品都写规格名称 + 规格值组合。**
6. **拿 `skuList: null` 当验收标准** → 这个字段对任何商品都是 null，包括商户自己的老商品；
   要看 `isMultiSku` + `specInfoList`（或看 update 的返回体）。
7. **素材入库报「容量已超出限额」** → 账号套餐配额，把 `size` 改成 1 照样报错，跟图片大小无关；
   页面那个「总容量使用 0%」也不可信。URL 不依赖入库，先跳过，配额解决后补登即可。
8. **一张损坏的源图会崩掉整个批次** → `sharp` 抛 `VipsJpeg: premature end of JPEG image`
   直接终止进程。必须每张图单独 `try/catch` + 清单落盘支持断点续跑（实测 249 个里有一个批次
   在第 202 个崩掉，续跑直接接上）。
9. **商品名称超 60 字符，整行废掉还连坐** → 报「商品名称超过限制」，同一商品的其它 SKU 行跟着报
   「同一商品的其他规格信息有误」。**补录别重导整批**（会把已成功的再建一遍），正确姿势是：
   读 `失败明细.xlsx` 的「商品编码」列 → 反查源数据 → 只生成失败那几个商品的行再导一次。
   实测 249 个商品分 3 批（109/177/162 行）导入，全批量 448 行最终 100% 成功。
   截断后别把后半截扔掉，**塞进 `subTitle`**（见 5.6）。
10. **「素材容量已超出限额」是假警报** → 真凶是 `productInstanceId` 错了一位
    （`24343333397` 写成 `24343313397`），后端把请求算到了另一个产品实例的配额上。
    容量一直够，页面那个「0%」也没骗人。配合 `user-agent` + `extendInfo` 一起补齐即可，
    补登 3,826 张实测 **91 秒、0 失败**。详见 2.7 / 2.8。
11. **小程序详情图被裁成半截** → `max-width:100%` 在小程序 `rich-text` 里不生效，
    必须写 `width:100%;height:auto;display:block`。判断方法：点开详情图能看全、页面里只显示一半。
12. **视频分组建到了图片分组里** → `createGroup` / `getGroupList` 靠 `materialType` 区分
    （图片 1 / 视频 3），建视频组时不传 3 就全跑到图片树里了。
13. **后台改完图，前台还是旧的** → 换无痕、加时间戳、清缓存都没用，因为**缓存不在浏览器**，
    在商城端的商品数据层。`queryGoodsDetail` 已经是新 URL，前台 H5/小程序仍渲染旧图。
    **别用前台页面判断更新成功与否**，看后台 API 返回值；前台要等平台缓存自然过期再抽查。
