# 13 · 批量操作铁律（开工前的检查清单）

> 这份不是接口文档，是**行为规范**。每次要对线上商品/素材/库存做批量写操作前，从头过一遍。
> 每条都来自真实事故，对应 `09-踩坑与事故复盘` 里的编号。

---

## 一、开工前 5 个固定动作

### 1. 先快照，且快照要覆盖"整个目标范围"

不是只存你要改的那几个字段，是整个对象的完整状态。

```js
// 落地到 backup/snapshot-<时间戳>.json
items.map(x => ({ id: x.id, 全部字段... }))
```

**为什么**：改错了要能逐字段回滚。`09-#14` 就是没有干净快照，导致"改了价格又改标题，价格被还原还查不出来"。

### 2. 先干跑（`--dry`），把计划打印出来

计划至少包含：**对象 → 现在值 → 目标值 → 依据**。

```
3032  晨光A5活页本  售价 10.2 → 10.2  (无变化，跳过)
3118  经典绘图圆规  售价 3.5  → 4.1   (源表真实价 4.1)
```

**为什么**：干跑一次能发现 80% 的逻辑错误（匹配错、映射错、数量不对），成本几乎为零。

### 3. 先拿 1 个做小样验证

完整走一遍：改 1 个 → 回读 → 确认字段真变了、其他字段没动。**再放开全量**。

**为什么**：`09-#13`（0 vs null）、`09-#17`（50 条上限）都是小样阶段就能发现的。

### 4. 大批量必须分批

单批 ≤ 50（保守点用 20~30），每批之间 `sleep` 几百毫秒。

**为什么**：接口有隐性上限，超了要么报错要么静默失败（`09-#17`）。

### 5. 验收标准提前定好

开工前就明确：**这次算"完成"的标准是什么**。默认是：

> **不带任何过滤条件的全量扫描，目标字段 100% 合规，非目标字段 100% 未变。**

**为什么**：`09-#15` 就是验收范围跟着修改范围走，结果两边一起漏。

## 二、改字段的 3 条铁律

### 铁律 1：删值传 `null`，不传 `0` / `''`

| 语义 | 传什么 | 反面 |
|---|---|---|
| 删除划线价 | `marketPrice: null` | `0`（变成"划线价 0 元"） |
| 清空副标题 | `subTitle: ''` 或 `null` | `' '`（一个空格，仍算有值） |
| 不设分组 | 不传 / 传 `null` | 传 `0`（可能指向某个真实分组 id） |

**验证也要跟着改**：判断"没填"用 `x == null`，不要用 `x !== 0`。

### 铁律 2：回写必须显式重建要改的字段

```js
// ❌ 危险：skuList 用的是详情里的旧快照，会被别的操作污染
const body = { ...tpl, ...d, title };

// ✅ 安全：显式重建
const body = {
  ...d,
  skuList: d.skuList.map(s => ({ ...s, salePrice: 目标价, marketPrice: null })),
  title,
};
```

**记住**：`...d` 只能带"完全不动"的字段。任何要改的字段，都在 body 里**显式写一遍**。

### 铁律 3：只改目标字段，其余一律原样带回

写之前先列一张"允许改动的字段清单"：

```
本次允许改：skuList[].salePrice, skuList[].marketPrice, title, subTitle
其余全部：原样
```

验收时逐字段比对**清单外**的字段，一个都不许变。
`09-#15` 之后我固定检查这 18 个字段：

```
minPoint, maxPoint, minPointPrice, maxPointPrice,
goodsStock, goodsLimitNum, goodsAvailableNum, goodsAlreadySoldNum,
isOnline, isCanSell, sort, title, defaultImageUrl,
priceType, soldType, goodsType, subGoodsType, outerGoodsCode
```

## 三、匹配 / 映射的优先级

永远是**从硬到软**，能停在前一级就别往下走：

```
① 业务主键      outerGoodsCode / goodsId / skuId
② 编码         货号、SKU 条码
③ 名称归一化   去空格/全半角/标点后比较
④ 名称相似度   仅在 ①~③ 全废时用，必须人工抽检
```

**反例**（`09-#18`）：用名称匹配 237 个只对上 78 个，换成 `outerGoodsCode` 后 306/306。
力气应该花在"找对主键"，不是"优化相似度算法"。

**映射类任务**（如二级分类→一级分类）：先把映射表写死成常量，干跑输出每个映射的命中数，
**0 命中的映射项要能解释**（是确实没这类商品，还是名字写错了）。

## 四、验收的 4 个检查（缺一不可）

| # | 检查 | 方法 | 不通过的含义 |
|---|---|---|---|
| 1 | **目标字段合规** | 全量拉，逐条比对期望值 | 没改到位 / 被覆盖 |
| 2 | **非目标字段未变** | 与快照逐字段 diff | 误伤（最严重） |
| 3 | **数量对得上** | 处理条数 = 计划条数，且 = 全量中的相关条数 | 漏处理 |
| 4 | **抽样人工看** | 挑 3~5 条看业务合理性 | 逻辑对但业务错 |

第 4 条最容易被忽略：
数字全对不代表对。`09-#13` 大米从 49.9 改到 128，字段层面完全"正确"，但业务上明显异常——
**改完价格必须看一眼"涨幅是否离谱"**。

```js
// 业务合理性护栏：涨幅超过 50% 的单独列出来给人看
const suspicious = rows.filter(r => r.now / r.before > 1.5 || r.now / r.before < 0.5);
```

## 五、出问题时的排查顺序

按这个顺序，别跳步：

```
1. 后台接口回读 → 值到底是多少？        （不看前台页面，见 09-#19）
2. 全量扫描     → 是个例还是普遍？      （别只看自己改过的那批）
3. 对比快照     → 哪些字段被动了？      （定位是哪一步改的）
4. 查操作时序   → 改完之后还有谁写过？  （09-#14 的根因）
5. 抓真实请求   → 界面手动做一次，diff 请求体
```

**第 1 步就能排除一半问题**：前台显示不对 ≠ 数据没改；接口返回成功 ≠ 数据改了。

## 六、写接口调用的固定骨架

```js
// 1. 从目标模块自己的页面拿鉴权头和 basicInfo（不要跨模块复用，09-#16）
await page.goto(目标模块URL);
// 监听 XHR 抓 headers + 一个真实请求的 body

// 2. 封装 post，错误码统一处理（注意 0 和 "0"，09-#4）
const post = async (ep, body) => {
  const t = await page.evaluate(...);
  const r = JSON.parse(t);
  if (!(r.errcode === 0 || r.errcode === '0' || r.code === 0)) throw new Error(...);
  return r;
};

// 3. 干跑 → 小样 → 分批 → 全量
// 4. 四项验收
```

## 七、一句话记住

> **改前有快照，改前先干跑；**
> **只动该动的，删值传 null；**
> **回写显式重建，批量必切片；**
> **验收看全量，不看自己改了几个。**
