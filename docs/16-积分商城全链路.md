# 16 · 积分商城全链路（加品 → 定价 → 可兑数量 → 限兑 → 分组）

> 实测日期：2026-11-11 ｜ 商户：`护稚佳品`（沿用 README 口径）
> `bosId` / `vid` / `wid` / 门店 KEY / 账号 / 票据一律以 `<BOS_ID>` `<VID>` `<KEY>` `<ACCOUNT>` `<TOKEN>` 占位，本文不含任何真实凭据。
> 范围：**19 个商品 / 39 个 SKU** 从「普通商品」加入积分商城并归入指定分组。
> 结果：19/19 加入、39 SKU 兑换价与可兑数量全部合规、分组 19/19 归位、积分商品总数 381 → **400**（精确 +19）。

本章补 [14](14-兑换商城排序重排与安全写入.md) / [15](15-批量改价与积分商城价格实战复盘.md) 缺的一段：**前两章讲的是"已经在积分商城里"的改（排序 / 改价），本章讲"怎么把一个普通商品加进积分商城"**，以及加进去之后必做的归位动作。

---

## 一、链路总览

```text
① 进积分商城列表 → 点「添加积分商品」
        ↓   （注意：是 window.open 新标签页，不是弹窗）
② 新标签 pointsMall/editGoods → 点「选择商品」→ 弹窗里单选一个商品
        ↓
③ 选兑换模式：纯积分 / 积分+金额
        ↓
④ 逐 SKU 打开「是否参加」开关（不开则输入框 disabled）
        ↓
⑤ 填 可兑换数量 / 积分价 / 现金价  → 设「每人限兑」
        ↓
⑥ 点「确认」→ POST mall/point/goods/addPointGoods
        ↓
⑦ 回读 queryPointGoodsListForManagement 逐 SKU 验收
        ↓
⑧ 【必做】归入分组：moveGoodsToClassify（不做就全挂在"系统分组"）
```

> **⑦⑧ 是最容易漏的两步。** 加入成功 ≠ 可用：不归组的话商品在后台挂在 `classifyId:0` 的「系统分组」里，列表上看不出归属，运营找不着。

## 二、入口：按钮会新开一个标签页

### 现象

点列表页右上「添加积分商品」毫无反应，反复找 `.klein-modal` 找不到弹窗。

### 两个叠加原因

| 原因 | 表现 | 处置 |
|---|---|---|
| 右上角**通知抽屉**浮在上面，透明遮罩吃掉点击 | 点击事件打到遮罩上，按钮看着"没反应" | 先关抽屉：找 `[class*=notification-drawer]` 的关闭按钮，或 `page.mouse.click` 打到按钮坐标 |
| 按钮是 `window.open` **新开标签页**，不是弹窗 | 原页面 DOM 永远不会有 `.klein-modal` | 用 `context.waitForEvent('page')` / `page.waitForEvent('popup')` 捕获新页面，在**新 page** 上操作 |

新标签的路由：

```text
/bos/products/ecGoodsmanage/<BOS_ID>/<KEY>/goods/pointsMall/editGoods
```

> **排查铁律**：点不动按钮时，先确认「它是不是在别的页面/标签里开」。在原页面死等弹窗是最常见的白耗时间。

## 三、接口名怎么拿到：扫 JS 包比点页面试错快一个数量级

猜接口名是最大的时间黑洞（曾经为找"加入积分商品"点了近一小时页面）。正确做法——**从已加载的前端资源里静态提取**：

```js
// 在页面上下文执行：列出所有已加载 js chunk
const urls = performance.getEntriesByType('resource')
  .map(r => r.name).filter(u => /\.js(\?|$)/.test(u));

// 逐个 fetch 回来，正则扫 /api3/ 路径
const found = new Set();
for (const u of urls) {
  const txt = await (await fetch(u)).text();
  for (const m of txt.matchAll(/["'`](mall\/point\/[a-zA-Z\/]+)["'`]/g)) found.add(m[1]);
}
```

一次性拿到 **20 个** `mall/point/*` 真实接口名（含 `addPointGoods`、`moveGoodsToClassify`、`updatePointGoods`、`updatePointGoodsLimitNum`……）。

> 换模块时把正则里的 `mall/point` 换成目标域即可。这招对任何 SPA 后台都通用，比"点按钮抓包"覆盖面大得多——**没被点到的功能也能拿到接口名**。

## 四、选择商品：弹窗是**单选**

「选择商品」弹窗是一个商品列表（带搜索），每行前面是 **radio**，不是 checkbox：

```text
一次只能加入一个商品 → 19 个商品 = 19 次走完表单，或
                     = 1 次走完拿接口模板 + 循环调接口（本次做法）
```

本次流程：第 1 个走完整 UI（顺便拿真实 `addPointGoods` 请求体）→ 回读小样通过 → 剩余 18 个用接口批量（4 批）。

## 五、表单顺序不可逆（这是本章最容易踩的坑）

| 顺序 | 动作 | 不这么做的后果 |
|---|---|---|
| 1 | 选商品 | — |
| 2 | 选兑换模式（纯积分 `priceType=2` / 积分+金额 `priceType=3`） | 模式不对，后面的"现金价"列不出现 |
| 3 | **逐 SKU 打开「是否参加」开关** | 不开开关时 `可兑换数量 / 积分价 / 现金价` 三个输入框是 **disabled**，`fill()` 会挂到 30s 超时 |
| 4 | 填值（可兑数量 / 积分价 / 现金价） | — |
| 5 | 设「每人限兑」 | 忘了就是默认不限兑 |
| 6 | 点「确认」 | 弹窗按钮是**「确认」不是「确定」** |

### 填值手段：必须走真实输入

Klein 的 `InputNumber` 是受控组件。用 `element.value = x` + `dispatchEvent` 改，**页面上看得到值、提交上去是空**：

```js
// ❌ 视觉有值，提交丢失
inp.value = 999; inp.dispatchEvent(new Event('input', { bubbles: true }));

// ✅ 走真实输入（Playwright locator，会触发完整的输入/失焦链路）
await page.locator('...').fill('999');
await page.locator('...').press('Tab');
```

### 表格里的「全部」批量行

SKU 表格第一行是「全部」（批量应用行）：在上面填一次，点「批量应用」下发到所有 SKU 行。适合所有 SKU 同值（如可兑数量都是 999）；**每个 SKU 兑换价不同的场景**（本次混合档位）要逐行填。

## 六、写接口：`addPointGoods`

```http
POST /api3/mall/point/goods/addPointGoods
Content-Type: application/json
authorization / apiclient / weimob-bosid / referer  缺一不可
```

```jsonc
{
  "basicInfo": { "...": "从积分商城页面自己的 XHR 抄，不要跨模块复用" },
  "solutionType": 2,
  "goodsId": 1617xxxxxxxxx,        // 普通商品的 goodsId
  "pickupSiteList": [],
  "classifyId": 0,                 // 0 = 系统分组（后面要 moveGoodsToClassify 改掉）
  "priceType": 3,                  // 2 纯积分 / 3 积分+金额
  "exchangeTimeType": 0,           // 0 不限时
  "exchangeStartTime": null,
  "exchangeEndTime": null,
  "visibleInNonExchangeTime": true,
  "goodsLimitNum": 1,              // 每人限兑
  "sort": 0,
  "applicablePeopleInfo": { "selectPeopleType": 1, "inApplicablePeopleTipInfo": { "tips": "你暂无资格参加活动" } },
  "skuList": [
    {
      "skuId": "3298xxxxxxxxx",    // ⚠️ 是商品的 skuList[].skuId，不是 itemSkuId
      "editChangeNum": 999,        // 可兑换数量（写字段）
      "point": 32,                 // 积分
      "pointPrice": 6.4,           // 现金部分；纯积分商品填 0
      "isPoint": true
    }
  ],
  "i18n": { "language": "zh-CN", "timezone": 8 },
  "extendInfo": { "refer": "/bos/products/ecGoodsmanage/<BOS_ID>/<KEY>/goods/pointsMall/editGoods", "source": 80 }
}
```

### 三个字段口径（和 [15 章](15-批量改价与积分商城价格实战复盘.md) 一致，这里再点一次）

| 语义 | 读字段（列表返回） | 写字段（提交用） |
|---|---|---|
| 可兑换数量 | `goodsAvailableNum`（= Σ `skuList[].availableChangeNum`） | `skuList[].editChangeNum` |
| 积分 | `skuList[].point` | 同名 |
| 现金 | `skuList[].pointPrice` | 同名 |

- **`skuId` ≠ `itemSkuId`**：商品详情/库存里的是 `itemSkuId`，积分接口要的是 `skuList[].skuId`。用错接口回 `result:true` 但商品是空壳。
- **纯积分商品现金填 `0`**（这是"没有现金"，不是"0 元"的反面——积分商品的 `0` 就是纯积分语义，和商品划线价的 `null` 规则不同）。
- **`skuList` 是整体覆盖语义**：改价时只传部分 SKU 会清空其余 SKU 的积分价；每单必须把要保留的字段显式带上。

## 七、加入成功 ≠ 归位：必须补分组

### 现象

19 个商品加进去后，列表里看不到归属分组（`pointClassifyInfo` 为空 / `classifyId=0`），运营在「学习文具」分组里找不到它们。

### 分组查询

```http
POST /api3/mall/point/classify/queryPointClassifyListWithPageForManagement
→ data.pageList[]: { pointClassifyId, name, ... }
```

> 该接口需要完整请求头；只带 `content-type` 会失败。头从页面任一 XHR 抄。

### 分组迁移

```http
POST /api3/mall/point/classify/moveGoodsToClassify
{
  "basicInfo": { "...": "..." },
  "goodsIdList": [ 1617xxxxxxxxx, ... ],     // 只放本次要归位的那批
  "pointClassifyId": 59584100397             // 目标分组 ID
}
```

**UI 路径**：列表勾选商品 → 「批量修改分组」→ 选目标分组 → 确认。弹窗里的分组下拉是 `klein-select`，用 `page.locator('.klein-modal .klein-select').first().click()` 展开，再点同名选项。

### 本次结果（守恒核对）

| 分组 | 条数 |
|---|---|
| 学习文具 | **192**（我方 19 + 历史 173） |
| 体育用品 | 80 |
| 家庭日用 | 55 |
| 读物潮玩 | 36 |
| 米面油品 | 28 |
| 少儿护理 | 9 |
| **合计** | **400**（= 加入前 381 + 19，守恒） |

## 八、验收（四项都要有）

1. **逐 SKU 合规**：`priceType` / 每个 SKU 的 `point` / `pointPrice` / 可兑数量 999 / `goodsLimitNum=1`，与计划表逐项 diff，**0 异常**。
2. **总数守恒**：加入前 `totalCount` → 加入后 `totalCount`，差值 == 目标商品数（本次 381 → 400，+19）。
3. **具体 ID 存在性**（比总数更硬的证据）：19 个目标 `goodsId` 逐个在列表中能查到。
4. **范围外零改动**：列表里其它带同样关键词（"铅笔"）的条目，`goodsId` 全部落在**早于本次的区间**（`16145xxxx` / `16147xxxx`，本次是 `16173xxxx`），确认是他人历史数据，未被动过。

> 数量会漂：`totalCount` 会被别人同时操作影响，**归因结论一律以具体 ID 是否存在为准**，不以总数准。

## 九、踩坑速查（本章新增）

| # | 坑 | 解法 |
|---|---|---|
| 1 | 点「添加积分商品」没反应 | 通知抽屉遮罩吃掉点击；先关抽屉 |
| 2 | 找不到弹窗 | 它是 `window.open` 新标签，要捕获新 page |
| 3 | 猜接口名浪费一小时 | 扫 JS chunk 正则提接口名 |
| 4 | 选品弹窗以为能多选 | 是 radio 单选，一次一个 |
| 5 | `fill()` 30s 超时 | 先开「是否参加」开关，否则输入框 disabled |
| 6 | JS 赋值有值、提交为空 | 受控组件必须走真实输入 |
| 7 | 提交成功但商品是空壳 | `skuId` 用成了 `itemSkuId` |
| 8 | 加进去了但分组里找不到 | `classifyId=0`，要 `moveGoodsToClassify` |
| 9 | 改价后可兑数量变 0 | `skuList` 整体覆盖，没带 `editChangeNum` |
| 10 | 弹窗「确定」点不到 | 按钮文案是「确认」 |

## 十、一句话记住

> **加品是"填一张表"，不是"点一个按钮"；填完还要归位，归位完还要逐 SKU 回读。**
> 入口先确认是弹窗还是新标签；输入先确认是不是 disabled；字段先确认读名和写名一不一样。
