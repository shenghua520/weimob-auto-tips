# 09 · 踩坑与事故复盘

> **26 个**真实踩过的坑，按坑到的顺序排。每条都有现象 + 根因 + 解法。
> 21~26 为 2026-11-11 积分商城 / 库存作业新增；开工前的动作清单见 [13 · 批量操作铁律](13-批量操作铁律.md)，整体流程见 [SOP · 作业流程](SOP-作业流程.md)。

## 1. 点侧边栏统计菜单 → 漏项

**现象**：遍历点击侧边栏统计功能数，得到 300 出头；接口返回 428。
**根因**：SPA 只渲染当前展开层，「员工」模块三级菜单侧边栏只显示到二级。
**解法**：菜单只认 `queryCacheableMenus` 接口，不认点击。

## 2. 菜单树归属判错 → 两棵大树合并

**现象**：店铺模块解析出 201 个节点（应该 113），里面混进了订单、售后、在售商品。
**根因**：用"树里出现最多的 productCode"判断归属，`home` 树里含订单菜单（`ecOrder`），数量压过 `home`。
**解法**：用**根节点**（第一个有 url 的节点）的 productCode。见 02 文档第 4 节。

## 3. pageSize 静默降级 → 误判"已清空"

**现象**：清库脚本返回"当前剩余 0 个"，但页面还显示 160 条。
**根因**：商品列表接口 `pageSize=200`，超出上限（20）后**不报错**，直接返回 `totalCount=0` + 空列表。
**解法**：固定 20 分页；每次传大 pageSize 前先用默认值验证 `totalCount` 是否合理。

## 4. errcode 类型不统一 → 成功被当失败

**现象**：素材列表"第1页失败: 处理成功"——errmsg 说成功，代码却走了失败分支。
**根因**：商品域 `errcode` 是字符串 `"0"`，素材域是数字 `0`；`if (err !== '0')` 对数字 0 成立。
**解法**：`if (!(err === 0 || err === '0'))`。

## 5. 忘记 authorization → fail auth

**现象**：重放请求返回 `{"errcode":1041,"errmsg":"fail auth"}`，但浏览器里同样的请求是好的。
**根因**：只带了 Cookie，没带 `authorization` 头（微盟的业务接口要双重凭证）。
**解法**：从页面 XHR 上抄 `authorization` / `apiclient` / `weimob-bosid` 三个头。

## 6. 猜删除接口名 → 三次 404

**现象**：`batchDeleteMaterial` / `removeMaterial` / `material/delete` 全 404。
**根因**：靠命名规律猜。
**解法**：在页面上做一次真实删除，抓请求。真名是 `material/center/material/deleteMaterial`。

## 7. 素材删除缺必填字段

**现象**：`{"errcode":11010000002,"errmsg":"updateUid不能为空, 组织架构Id不能为空, 素材类型不能为空"}`。
**根因**：`updateUid` 传了当前登录人 / 没传 `materialType`。
**解法**：`updateUid` 必须用**该素材的 `createUid`**（谁传的填谁），`materialType` 从素材记录里取。

## 8. 库存调整"成功"但数值不变

**现象**：12 条库存提交调整，接口 `result:true` + `taskId`，回读数值纹丝不动。
**根因**：① 是**异步任务**；② 更致命的是商品已删、SKU 不存在，任务没有落点。
**解法**：库存清零要在删商品**之前**；异步接口一律回读验证。

## 9. 覆盖更新填 0 被拦

**现象**：想"覆盖更新为 0"清零，提交后无变化。
**根因**：调整数量输入框最小值为 1，0 被前端拦掉（提示不明显）。
**解法**：改用"增量更新 → 减少 N"，N 取当前实物库存。

## 10. playwright-cli 跨域掉会话

**现象**：`open master.weimob.com` 后跳 `account.weimob.com`，下一条命令报 `Browser 'weimob' is not open`。
**根因**：CLI 的会话绑定在页面 CDP 上，跨域跳转后连接失效。
**解法**：改用自建 Playwright 脚本 + `launchPersistentContext`，登录态存 profile 目录。

## 11. 浏览器版本不匹配

**现象**：`Executable doesn't exist at .../chromium-1246/chrome-win64/chrome.exe`。
**根因**：playwright-core 版本要 1246，本机缓存只有 1243。
**解法**：`launchPersistentContext(..., { executablePath: '<缓存里的 chrome.exe>' })` 显式指定，别去下载。

## 12. 内容在 iframe 里 / 弹窗被遮罩挡住

**现象**：`document.body.innerText` 只有侧边栏；点弹窗元素一直 `Timeout ... intercepts pointer events`。
**根因**：微盟页面的业务内容常套 iframe；下拉/弹窗上方盖着透明 `input`。
**解法**：
- 取文本：遍历 `page.frames()`，取内容最长的那个
- 点击：`click({ force: true })`，或点底层 `input[role=combobox]`

## 13. 把「不填」当成「填 0」→ 划线价变成"¥0"

**现象**：要求「市场价（划线价）全部不要了」，我传 `marketPrice: 0`。接口返回成功，回读也是 0，
但前台/后台编辑页里划线价那一栏仍是个价格字段，语义是「划线价 = 0 元」而不是「没有划线价」。

**根因**：`0` 是**值**，`null` 是**无值**。两者在业务上完全不同。
微盟的空价格字段（如 `adviseSalePriceMin`）返回的都是 `null`，说明「不填」的表示就是 null。

**解法**：删字段一律传 `null`，不要传 `0` 或 `''`。

```js
skus.map(s => ({ ...s, marketPrice: null }))   // ✅ 不填
skus.map(s => ({ ...s, marketPrice: 0 }))      // ❌ 填了个 0
```

**验证方式**：回读时判断 `s.marketPrice != null`（而不是 `!== 0`），才能真正确认"没填"。

## 14. 用 `...d` 展开回写商品 → 被旧快照污染，改动被还原

**现象**：先批量改了售价（成功，验证通过），随后批量改标题。改完标题再查，
发现有几个商品的**售价退回了改前**。反复"清干净→又冒出来"，查了两轮才定位。

**根因**：改标题的脚本里 body 是这么拼的：

```js
const body = { ...tpl, ...d, title, subTitle };   // d 是当时拉的详情
```

`d.skuList` 里带着的 `marketPrice` / `salePrice` 是**那一刻的快照**。
只要中间有其他操作改过价格，这个陈旧快照一回写就把新值盖回去了。
更隐蔽的是 `tpl`（模板骨架）里还硬编码了某个商品的 `skuList`，一旦 `...d` 没覆盖到就污染得更彻底。

**解法**：**任何回写都必须显式构造要改的字段，不依赖快照展开**。

```js
const body = {
  ...d,
  skuList: d.skuList.map(s => ({ ...s, salePrice: 目标价, marketPrice: null })),  // 显式重建
  title, subTitle,
};
```

**教训**：`...d` 只适合"原样带上不需要改的字段"，**凡是要改 SKU 级字段，就把 skuList 整个重建一遍**。

## 15. 只验证自己改过的那批 → 漏掉一大半

**现象**：清市场价，验证脚本只遍历"我处理过的 249 个商品"，报告 ✅ 全通过。
用户一眼看出"还有很多商品划线价没删"。全量扫描发现另有 20 个商品 33 个 SKU 残留。

**根因**：验证范围和修改范围绑定，但**修改范围本身就是漏的**
（有 58 个商品不在源表里，走的是另一条路径，从没进过我的清单）。

**解法**：**验收标准永远是"全量扫描 = 0 残留"，不是"我改了 N 个都成功"**。

```js
// 错：只查自己改过的
targets.forEach(check)

// 对：拉全量，检查是否还有不合规的
const all = await fetchAllGoods();          // 307 个，不管改没改过
all.forEach(g => assert(g.skuList.every(s => s.marketPrice == null)));
```

**推论**：任何"清空/统一某字段"的任务，最后一步必须是**不带过滤条件的全量审计**。

## 16. 跨模块照抄 `basicInfo` → 打到了另一个产品实例

**现象**：素材入库一直报「素材容量已超出限额」，但素材页显示用量 0%，且把图片 size 改成 1 byte 也照样报错。

**根因**：这个商户有**两套产品实例**，各自的 `basicInfo` 不一样：

| 模块 | productId | versionId | productInstanceId | 素材额度 |
|---|---|---|---|---|
| 素材 / 小程序 | 1 | 110499 | `24343333397` | 1536000 |
| 商品 / 库存 | 145 | 112519 | `24343313397` | **0** |

我从**商品模块**抄的 `basicInfo` 去调**素材接口**，后端拿 `24343313397` 去查额度，查到 0 → 报超限。

**解法**：`basicInfo` **必须从目标模块自己的页面抓**，不能跨模块复用。
排查时用两个 ID 各调一次额度查询，看 `capacity` 就能分辨。

**顺带澄清两个易混的单位**：`capacity: 1536000` 单位是 **MB**（1.5TB），
`count: 439` 是已用 **MB**。439MB ÷ 1.5TB = 0.03%，所以页面显示 0% 是真的。

## 17. 批量接口的隐性上限 → 静默/显式失败

**现象**：积分商品批量改分组，`goodsIdList` 传 183 个直接报
`{"errcode":"001450020000101","errmsg":"列表[goodsIdList]超过[50]限制"}`。

**根因**：批量接口普遍有单次条数上限。已知的：

| 接口 | 上限 | 超限表现 |
|---|---|---|
| `mall/point/classify/moveGoodsToClassify` | **50** | 显式报错 |
| `queryGoodsListWithPageForManagement` | **20**（pageSize） | **静默返回空列表** |
| `insertMaterial` | 单条 | — |

**解法**：批量前先按 50（或更小）切片，并且**不要假设超限会报错**——
分页类接口超限是静默降级，必须用 `totalCount` 交叉验证。

## 18. 按名称"相似"匹配 → 错配；按 ID 精确匹配 → 100%

**现象**：给源表填微盟价格，第一版用商品名匹配，237 个只对上 78 个；
改用名称归一化 + 货号后到 233 个；最后发现**用商品ID（outerGoodsCode）匹配，306/306 全中**。

**根因**：名称里有截断（58 字上限）、全半角、空格、编码前缀等噪声，
而 `outerGoodsCode` 是导入时写进去的**业务主键**，一比一个准。

**解法**：匹配优先级固定为
**① 业务主键（outerGoodsCode / goodsId） → ② 编码（货号） → ③ 名称归一化 → ④ 名称相似度**。
能用 ① 就绝不往上走。相似度匹配只在万不得已时用，且必须人工抽检。

## 19. 用前台页面判断"改成功了没" → 假失败

**现象**：改完商品图，后台接口 `queryGoodsDetail` 返回的已是新 URL，
但手机端页面还在显示旧图。换无痕模式、加时间戳参数都一样。

**根因**：缓存在**商城端商品数据层**，不是浏览器缓存。
后台业务库更新了，前台渲染层要等平台同步。

**解法**：判断写操作成败**只看后台接口回读值**，不看前台页面。
前台要验证，等缓存过期后单独抽查。

## 20. 标题被截断 → 拆名规则漏项 + 把品牌词当编码

**现象**：把「开头长编码」的商品名拆成「中文主标题 + 编码副标题」，63 个都改对了，
但用户截图指出某个商品标题里**还带着编码**。

**根因**：两个叠加问题
1. 微盟标题有 **58 字上限**，那个商品原名 83 字，标题里只剩 `ZCPN0383/.../ZCPN0387 MG KIDS食品级软头`，
   编码串本身就把标题占满了，我的"编码 + 空格 + 中文"正则匹配失败 → 整个跳过。
2. 编码后面夹了个**英文品牌词 `MG KIDS`**，正则把它当成编码的一部分，于是 `code` 里混进了品牌词。

**解法**：
- 拆名要基于**源表完整名称**（`上架商品完整明细`），不是微盟被截断的标题
- 编码边界用**已知货号集合**去切，或用"最后一个编码 token 之后"定位，不要用"第一个中文字符"
- 拆完必须**回读校验**：`title` 不含编码、`subTitle` 含编码

## 21. 通知抽屉的透明遮罩吃掉点击 → 以为按钮坏了

**现象**：积分商城列表页点右上「添加积分商品」，毫无反应；换 `click({force:true})`、换 DOM `click()` 都没用。

**根因**：右上角**通知抽屉**的遮罩层浮在按钮上面，`offsetParent` 正常、`pointer-events` 也正常，但点击全打在遮罩上。元素能查到、能"点"，就是没反应。

**解法**：
- 点之前先关掉通知抽屉（`[class*=notification-drawer]` 里的关闭按钮）
- 或者直接对按钮坐标 `page.mouse.click(x, y)`（坐标点击能绕开大部分遮挡）
- 判断遮挡：`document.elementFromPoint(x, y)` 看返回的是不是你以为的那个按钮 —— **这一招能立刻证伪"按钮没反应"**。

## 22. 按钮不是弹窗，是新开了一个标签页

**现象**：`window.open` 打开的编辑页，一直在原页面等 `.klein-modal`，等了一小时。

**根因**：点「添加积分商品」是 `window.open` → **新标签** `pointsMall/editGoods`，原页面 DOM 永远不会有弹窗。

**解法**：先 `const p = await context.waitForEvent('page')`（或 `page.waitForEvent('popup')`）再点按钮；后续所有操作在**新 page** 上做。
**通用判断**：点击后原页面 DOM 无变化 → 先看 `context.pages()` 是不是多了个页面，别急着改选择器。

## 23. 受控组件用 JS 赋 `value` → 页面有值、提交是空

**现象**：`inp.value = 999; dispatchEvent('input')` 之后截图里输入框显示 999，提交后服务端收到空值。

**根因**：Klein `InputNumber` 是受控组件，值存在 React state 里。直接改 DOM 只改了显示，没进 state。

**解法**：走真实输入 —— `page.locator(sel).fill('999')` 然后 `press('Tab')` 触发失焦。
**前提**：确认输入框没 `disabled`。disabled 时 `fill()` 会挂 30 秒超时——先打开控制它的开关（如「是否参加」）。

## 24. 入库单 `defectiveQty` 填错 → 残次 999 → 纠错又少 1 个

**现象**：给 39 个新 SKU 录 999 库存，误把 `defectiveQty` 也填成 `999`，实物库存显示 999 但残次也是 999。
用报废单（`bizType:"1206"`）冲减残次，`quantity` 被前端组件自动抬成 **1**，只冲掉 1 个，实物变成 998。

**根因**：① 不理解字段语义就填了值（`defectiveQty` = 残次品，正常入库一律 0）；② 纠错动作本身没走小样 + 回读。

**解法**：报废单 `quantity` 要用真实输入改（不是 JS 赋值）、提交后回读；实物差 1 个靠再补一张 `quantity:1` 的入库单补齐。
**教训**：**纠错也是写操作，也要走小样闭环**——否则"修 bug"会造新账。

## 25. 「加入成功」≠「归位」→ 商品全挂在系统分组

**现象**：19 个商品加进积分商城，接口全成功、列表也能查到，但运营在「学习文具」分组里找不到它们。

**根因**：加入时没传 `classifyId`，默认落 `0`（系统分组）。列表上用 `pointClassifyInfo` 才看得出归属，不看这个字段会误判"已经好了"。

**解法**：加品后补一次 `mall/point/classify/moveGoodsToClassify { goodsIdList, pointClassifyId }`，再回读 `pointClassifyInfo.name` 确认。
**推广**：凡是后台有分类维度的对象（商品分组、积分分组、素材分组），落库后必须补一次归类并回读。**"加进去"和"放对位置"是两件事。**

## 26. 「二舍三入」当成四舍五入 → 价格差 0.1

**现象**：两条 SKU 兑换价算成 6.2 / 5.6，按规则应为 6.3 / 5.7。

**根因**：「二舍三入」= 保留 1 位，**第 2 位小数 0/1/2 舍、3~9 进**（6.24 → 6.3）。我按 `Math.round` 理解，把 6.24 舍成 6.2。

**解法**：凡涉及舍入口径，先用**真实数据样例**跑一遍给用户确认（拿 3~5 个临界值：x.x2 / x.x3 / x.x4），确认后再全量。
**教训**：规则里的"边界值"和"舍入方式"必须显式问，不能靠语感补全。

## 一句话复盘

> **能查接口就别点页面；能回读就别信返回值；能先备份就别急着删；顺序错了回不去。**
