## 一、任务与最终结果

### 规则演进（3 版，都是用户口头给的，靠干跑样例逐条确认）
| 版本 | 售价 | 兑换价分档 |
|---|---|---|
| v1 | 进价 × 1.5，二舍三入保留 1 位 | ≤4 纯豆；4~5 为 1元+豆；>5 为进价+豆 |
| v2 | 不变 | ≤3 纯豆；3~4 为 1元+豆；4~5 为 **2元+豆**；>5 为「网上进价」+豆 |
| 补充 | 不变 | 可兑换数量每 SKU 999、每人限兑 1 |

- **二舍三入** = 保留 1 位小数，第 2 位小数 0/1/2 舍、3~9 入（例 4.27×1.5=6.405 → 6.4）。
- **1 元 = 10 豆，1 豆 = 1 角，不是 1 分**；豆 = 金额 × 10。售价与现金都保留 1 位，所以豆数天然是整数。
- 「网上进价」= Excel 的「拿货价」（晨光联盟商城采购价）按二舍三入保留 1 位，留一点空间；现金 4.27 → 4.3，豆 =(6.4−4.3)×10 = 21。

### 最终结果（全程 0 误改、0 写入失败）
| 项目 | 结果 | 独立复核 |
|---|---|---|
| 商品售价（WOS `price-update`） | 185 商品 / 383 SKU 行 | 全量 454 回读：185 目标合规，**269 范围外 0 变动** |
| 积分商城兑换价（`updatePointGoods`） | 185 商品（含 2 个混合商品等价处理） | 全量 393：目标 0 异常，**208 范围外 0 改动** |
| 可兑换数量 / 限兑 | 每 SKU 999、限兑 1 | 185 目标 0 异常、208 范围外 0 改动 |
| v2 规则改版 | 只重算 68 行、**只写 45 个商品** | 同上，兑换价/可兑/限兑 0 异常 |
| Excel 副本 | 383 行 I/J/K 更新 | 回读 0 异常，383 张浮动主图、下拉、另 2 个 sheet 保留 |

## 二、成功的做法（可复用）

### 1. 三条通道各司其职，不混用
- **商品售价** → WOS 官方 `woscli goods price-update`，有 `--dry-run`，只传 `skuId + salePrice`；OAuth 授权，凭据不落盘。
- **积分商城兑换价 / 可兑数量 / 限兑** → WOS 26 个域里**没有** `point-goods` 域，只能走后台 `api3/mall/point/goods/updatePointGoods`。
- 查询基线用 `admin-api query-goods-list`（454 商品）与 `queryPointGoodsListForManagement`（393 积分商品）。
- 结论：**先查 WOS 能力边界，再决定要不要逆推后台接口**；别因为一次实战用过 `api3` 就默认所有写操作都走它。

### 2. 快照 / 回滚体系（每一轮写操作都重做一遍）
- 写前快照：Excel 源表副本、WOS 商品全量 454、SKU 级详情 185、积分商城全量 393（多时点）。
- 回滚文件**写入前落盘 + 立刻回读校验条目数**，schema 全局唯一，且只记录本次真正会写的对象。
- 每轮都换一批带 ISO 时间戳的文件名，不覆写旧快照。
- 所有试探性写入的小样**一律自动回滚**，线上零残留后才允许批量。

### 3. 精确匹配，零模糊
- 表格**没有** `goodsId` / 商品编码列，但商品名里嵌唯一编码（多数在副标题）。用它 + 名称归一化 + 「表格旧售价 = 微盟现价」二次消歧，做到 **185/185 精确匹配**。
- 3 个多候选/漏召回商品用**人工确认映射**补齐，每条都写清依据（标题逐字一致 / 只差一个空格 / 现价一致）。
- SKU 行 **383/383 精确对齐 `skuId`**：12 行走规格条码、371 行按规格值，**零相似度匹配**。
- 表格旧售价与微盟 SKU 现价 0 处差异，既验证主键没配错，也提供了消歧维度。

### 4. 固定五步（每轮都跑，不因为「上次成功过」就跳过）
`全量快照 → --plan 干跑（对象/现值/目标值/依据）→ 1 个商品小样（改→回读→非目标字段未动→自动回滚）→ 分批写入（失败 >3 中止）→ 另起只读会话独立复核`

### 5. 最小化写入
- v2 改版时先 diff：只有 68 行变化、涉及 45 商品，其余 **140 个商品一行没写**。
- 只改目标字段：WOS 只传 `salePrice`；`updatePointGoods` 只带 `{skuId, editChangeNum, point, pointPrice, isPoint}`；不动 `costPrice`/`marketPrice`/库存/条码。
- 发现「表格拿货价 vs 微盟 costPrice」9 个商品不一致（差到 3 倍）时**按纪律暂缓、只报告**，等用户明确「按 Excel 拿货价」才补改。

### 6. 独立复核不复用写入脚本的运行时结果
- 另起 Playwright 会话重新拉全量列表，与写前快照逐商品 diff。
- 必须同时验「**范围外 0 变动**」，不能只验自己改过的那批。
- `STATIC` / `VOLATILE` 分层：`goodsAvailableNum` 等自然波动只报告、不判失败、绝不顺手改回去。

### 7. 从前端 JS 反查真实字段（比试错快一个数量级）
- 复用旧脚本的扫描法：`performance.getEntriesByType('resource')` 取所有 JS → `fetch` 后搜关键词。
- 一次扫出：列表列 `title:"可兑换数量", key:"editChangeNum"`、提交处 `skuList.map(e => ({skuId, editChangeNum: e.availableChangeNum, ...}))`、以及 20 个 `mall/point/**` 接口清单。
- **读写字段名不一致**是这次最大的坑：读 `availableChangeNum`，写 `editChangeNum`。

### 8. Excel 的 XML 级最小化改写
- 不用 openpyxl 重存（会丢浮动图片/数据验证），而是**只正则替换 `xl/worksheets/sheet1.xml` 里 I/J/K 的 `<c>` 单元格**，其余 zip 条目原样复制。
- 结果：383 张浮动主图、下拉校验、另 2 个 sheet 100% 保留；源文件（微信临时目录）始终未动，只交付工作区副本。

### 9. 规则歧义一律先干跑，不猜
二舍三入定义、3~4 元区间、多 SKU 进价不同、豆子换算、"网上进价"含义 —— 全部用**表里的真实数字**跑样例给用户过目，拿到确认才动手。

### 10. 用户给的方案走不通时：先证伪，再给等价实现
用户要求「分两次上积分商城、每次只选一部分 SKU」。小样证明接口不支持后，给出**实测证据**（另一批 SKU 被清成 null、第二次报「至少要有一个积分sku」），再用「整单一次提交 + priceType=3 + 纯豆 SKU 现金 0」实现其真实意图，并如实说明唯一的展示差异。

## 三、失败与踩坑（现象 / 根因 / 解法）

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | WOS 商品列表传 `--page-size 50` 只返回 20 条，一度以为「上限 20」 | `admin-api query-goods-list` **只认 camelCase `--pageNum/--pageSize`**，kebab-case 被静默忽略 | 实测四种参数组合；快照脚本加「第 1 页与第 2 页首 ID 必须不同」的校验，不满足就中止，避免产出假快照 |
| 2 | 后台登录后 URL 是 `/bos/console/solution`，没有门店 KEY | 账号停在「请选择您的主营行业」引导页 | 从本机回收站里的旧脚本找到已验证的真实 `<KEY>`；直接打开 `/goods/list` 抓鉴权头与 `basicInfo` |
| 3 | 用 `vid` / `wid` 当 KEY → 「页面加载出错」/「您没有该店铺权限」 | KEY 不是组织 ID | 同上；别把 bosId/vid/wid 拼成页面 URL 猜 |
| 4 | 两个 Playwright 脚本同时跑 → `Target page, context or browser has been closed` | 共用同一个 `launchPersistentContext` profile 目录 | 浏览器任务**串行**，或各用独立 profile |
| 5 | UI 拦截写请求「captured writes: 0」 | 积分商城列表的「编辑」是图标按钮，按文本 `getByText('编辑')` 点不中 | 改走「详情结构作骨架 + JS 扫描字段」的小样试错；拦 UI 不是万能的 |
| 6 | 改可兑数量时传 `availableChangeNum` / 完整 SKU 对象 / 顶层 `goodsAvailableNum`，接口都回 `result:true` 却毫无变化 | **写字段名是 `skuList[].editChangeNum`**，且 skuList 只收 5 个字段、顶层要带 `classifyId`；多余字段被后端忽略 | 扫前端 JS 定位；小样验证后批量。再次印证「返回成功 ≠ 数据改了」 |
| 7 | `updatePointGoodsLimitNum` 传各种数量参数都无效 | 该接口只管 `goodsLimitNum`（缺了直接报「参数: goodsLimitNum 为空」） | 可兑数量走 `updatePointGoods`；接口职责别按名字猜 |
| 8 | 分两次提交、每次只带一部分 SKU → 另一批 SKU 的 `point/pointPrice` 被清成 `null` | `updatePointGoods` 的 `skuList` 是**整体覆盖**，不是增量追加 | 整单一次带全部 SKU；纯豆组用 `priceType=3` + 现金 0 等价表达 |
| 9 | 上述第 2 次提交报 `001450020000101 至少要有一个积分sku` | 第一次把另一批 SKU 清空后，商品已无有效积分 SKU | 失败小样自动回滚（完整 `skuList` + 原 `priceType`），零残留 |
| 10 | 独立复核首次报 1 个异常：`minPointPrice` 实际 5.9、期望 1.0 | 列表 `minPointPrice` 取「**最小积分那个 SKU**」的现金，不是所有 SKU 现金的最小值（该商品最小积分 30 对应 5.9 元） | 用详情接口逐 SKU 回读确认数据无误，修正**复核口径**后 PASS；是验算错，不是写错 |
| 11 | 改完兑换价后，差点把刚设好的可兑数量 999 清回 0 | `updatePointGoods` 不带 `editChangeNum` 就会重置该字段 | 每单强制带 `editChangeNum: 999` + `goodsLimitNum: 1`，小样专门验「兑换价变了、999 还在」 |
| 12 | 9 个商品的进价两个来源差到 3 倍（2.5 vs 7.5） | Excel「拿货价」= 晨光联盟商城采购价；微盟 `costPrice` = 后台人工维护值，不是同一个数据源 | 不擅自选，列出两种口径的售价让用户拍板；确认后按 Excel 补改 |
| 13 | 复核脚本 `UnboundLocalError: Number` | Python 里函数定义在调用之后（放在 `main()` 内），被当成局部变量 | 改成内联 `int(x or -1)`；修完重跑，数据未受影响 |
| 14 | 生成 HTML 预览两次报 `unsupported format character ';'` | CSS 的 `width:100%` 与 Python `%` 格式化冲突 | 写 `100%%`，或改用 f-string / 拼接 |
| 15 | 独立复核脚本 `unknown flag: --goods-id`（偶发） | woscli 瞬时参数解析异常，手动重跑同命令正常 | 不复用同一接口做复核，改走**另一条只读接口**（全量 `query-goods-list`）做 diff，反而更符合独立复核原则 |
| 16 | v1 规则「≤4 纯豆」用户后来改成「≤3 纯豆 / 3~4 1元 / 4~5 2元」 | 业务规则本就会迭代 | 因为每轮都留了干跑表和回滚文件，改版只需重算 68 行、写 45 商品，而不是全量重刷 |

### 反模式清单（下次直接避开）
- ❌ 只看接口返回值 `result:true` / `errcode:0` 就宣布成功。
- ❌ 用「详情接口读出来的字段名」直接回写，不验证写字段名。
- ❌ 把 `skuList` 当增量列表，只传要改的那几个 SKU。
- ❌ 只验「自己改过的那批」，不扫全量、不验范围外。
- ❌ 规则有歧义就按常识补齐（尤其金额、区间边界、单位换算）。
- ❌ 用 openpyxl 重存带浮动图片/下拉的 xlsx。
- ❌ 多个浏览器任务共用一个持久化 profile。
- ❌ 发现范围外的数据问题顺手「修一下」。

## 四、方法论沉淀

1. **能查接口就别点页面；能回读就别信返回值；能先备份就别急着删；顺序错了回不去。**
2. **判断写操作成败只看后台接口回读值**，不看前台页面（缓存在商城端数据层）。
3. **匹配优先级**：业务主键 / 唯一编码 → 编码货号 → 名称归一化 + 价格消歧 → 人工确认映射；相似度只做兜底。
4. **允许改动清单按任务重列**，不照抄上一份；验收时逐字段 diff 清单外字段。
5. **复合字段要一起带回**：一次写入可能连带重置上一轮刚设的字段，先想清楚「这单会不会把它冲掉」。
6. **用户方案被证伪时**：给证据、给等价实现、说明差异，不硬套也不擅自换方向。
7. **用户长期纪律**：先记录原始数据再动手；用户没点名的一律保持原样；发现范围外问题只报告、等确认。
