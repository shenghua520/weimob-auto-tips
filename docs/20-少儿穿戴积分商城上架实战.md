## 一、本次用户口径（三条硬约束）

| # | 用户原话 | 落地口径 |
|---|---|---|
| 1 | 「有些商品状态是无库存 别乱加」 | 只上架 **SKU 物理库存 `editQuantity` > 0 且 `isDisabled !== true`** 的商品；零库存商品整类不进商城 |
| 2 | 「书包兑换区库存都设置50 不要多」 | SKU 级可兑数量 `editChangeNum = 50`（注意：**不是** 19 章体育用品那次的 999，可兑数量按次指定，不是常量） |
| 3 | 「限制兑换1个也要有 然后兑换分组和排序你别忘了」 | `goodsLimitNum = 1` + `classifyId` 直传「少儿穿戴」积分分组 + 按 docs/19 规则重排 sort |

> 坑：物理库存（`editQuantity`）与可兑数量（`editChangeNum` / 回读 `availableChangeNum`）是**两个不同字段**。前者决定"能不能上架"，后者是上架后"每人可兑多少"。混用会把有货商品判成没货、或把可兑数写成 999。

## 二、库存分层（本轮核心发现）

积分商城「少儿穿戴」组原本只有 **4 个零库存商品**（矫正带 / 鞋垫 / 眼镜 / 坐姿矫正器，gid `161935xxx` 段），书包类 **0 个**。
把商品库「少儿穿戴（兑换）」孪生组（`16532704100397`，`isShow=false`）的 21 个书包兑换复制体拉详情后：

| 类别 | 商品数 | SKU 物理库存 | 处置 |
|---|---|---|---|
| 书包类兑换复制体 | 21 | 400 ~ 9990，全有货 | ✅ 上架 |
| 背部矫正带 / 鞋垫 / 儿童防蓝光眼镜 | 3 | **全部 SKU `editQuantity = 0`** | ❌ 不上架（就是用户说的"无库存别乱加"） |

## 三、`addPointGoods` 直接落组，不用再 move

```jsonc
{
  "basicInfo": { ...模板头... }, "solutionType": 2,
  "goodsId": 161785126100397,
  "classifyId": "59464100397",        // 少儿穿戴（积分一级分组）—— 直传即归位
  "priceType": 3,                      // 现金 + 积分
  "goodsLimitNum": 1,                 // 每人限兑 1
  "sort": 0,                           // 新品先 0，随后由 updatePointGoodsSort 统一重排
  "visibleInNonExchangeTime": true,
  "skuList": [
    { "skuId": 330120280100397, "editChangeNum": 50, "point": 222, "pointPrice": 66.8, "isPoint": true }
  ]
}
```

- `skuId` 取商品 `skuList[].skuId`，**不是** `itemSkuId`。
- `classifyId` 直传目标积分分组即完成归位，省掉 `moveGoodsToClassify`。
- 顶层其余字段照抄列表模板头（`basicInfo` / `i18n` / `extendInfo`），缺壳字段会被静默拒绝。

## 四、删除（回滚用）：body 必须带壳字段

```jsonc
{
  "basicInfo": { ... }, "solutionType": 2,
  "goodsIdList": [161785126100397],
  "i18n": { "language": "zh-CN", "timezone": 8 },
  "extendInfo": { "refer": "goods/pointsMall/index", "source": 80 }
}
```

只传 `goodsIdList` 会 **静默失败**：接口返回非 0 errcode，函数判 `false`，但商品还在（列表总数不变）。
本次小样回滚因此残留 2 条，用独立脚本 `105-cleanup-sample-residue.js` 按"删前留档 → 删 → 逐条回读确认消失 → 比对总数变化"清理干净（429 → 427）。

## 五、排序：总价只算"实际参加兑换"的 SKU

积分详情 `queryPointGoodsDetailForManagement` 回读的是**全部 SKU**，未参加兑换的 SKU `point = 0`，
直接 `min(point/10 + pointPrice)` 会把总价算成 0，排序全乱。

```js
const isPart = s.isPoint === true || Number(s.point || 0) > 0;   // 只统计实际参加兑换的
```

修好后书包组内总价严格升序：¥59.9 → 69 → 69 → 69.9 → 79 → 79 → 79.9 → 89 → 89 → 89 → 99 → 109 → 128 → 129 → 129 → 139 → 139 → 149 → 149 → 159 → 179。

### 二级分组 sort 的权威来源

积分商城页面上下文调 `mall/goods/queryGoodsDetail` **拿不到 `goodsClassifyList`**（返回空）。
正确做法：二级分组 sort 取 **商品分组树**（`queryClassifyListWithPageForManagement` 按 parentId 逐个查，共 18 一级 + 220 二级），
商品→二级分组的归属取 **商品库详情快照**（`queryGoodsDetail` 在商品库页面上下文有 `classifyList`）。

本轮两个二级分组：`书包（兑换）` sort=4、`健康体态（兑换）` sort=0 —— 按 sort 降序，书包组在前。

**独立性的关键**：期望值全部取"写入前的独立产物"，不复用写入脚本回读——

| 期望 | 来源（写入前） |
|---|---|
| 加品期望（point/pointPrice/可兑 50/限兑 1） | `.scan/shaowear_addpoint_plan.json`（写入前计划） |
| 排序期望（newSort / 二级分组 / 总价） | `backup/107-sort-plan-shaowear_*.json`（独立脚本 107 只读产出） |
| 写前全量基线（427 条） | `backup/99-sort-baseline_*.json`（独立脚本 99 在 00:58 产出，早于任何写入） |

判"不多不少"用 **集合差**（现网 ID 集合 − 基线 ID 集合 === 计划新增 ID 集合），而不是比总数。

## 八、一句话记住

**先按物理库存筛商品，再按用户指定值写可兑数量；加品直传 classifyId 归位；排序用专用接口只改 sort；总价只算参加兑换的 SKU；复核必须换脚本换基线，用集合差判多寡。**
