# 18 · 商品复制改组 + 积分商城整体替换实战

> 实测日期：2026-11-16 ｜ 两个写作业合并复盘：① 512 商品全量复制并改入（兑换）分组；② 400 积分商品整体换成（兑换）复制体。
> 结果：512/512 复制改组成功（22 个多分组商品逐组映射）；400/400 积分替换成功、原条目清空、分组零差错。
> 前置：[17 · 分组整树复制](17-商品分组整树复制实战.md)（先有（兑换）分组树和复制体）。

## 一、作业①商品复制改组：复制是前端跳转，不是接口

### 真实链路（拿 payload 花了 5 轮取证才定型）

```text
列表行「更多 → 复制」→ 前端跳转 goods/editNoMenu?id=<goodsId>&type=sale&isCopy=true
        ↓ （表单全预填，与原商品一模一样）
只改分组 → 点保存 → POST mall/oods/copyGoods（整张表单的 payload）
```

**没有独立的 copy 接口**——`copyGoods` 就是新增保存，payload 是完整表单（specInfo/price/sku 全带）。批量时可**直连 `isCopy=true` URL** 逐商品构造请求，不用点表格，512 个约 3 分钟。

### 分组改写：只动两个字段

```jsonc
{
  "goodsClassifyList": [ { "classifyId": <兑换组id>, "name": "...（兑换）", "parentId": <兑换父id> } ],
  "goodsClassifyIdList": [ <兑换组id>, ... ],
  // 其余字段（goodsId/sku/价格/图片…）原样透传，一个不碰
}
```

**映射规则**：源组 → 名字+「（兑换）」的孪生组，**按 classifyId 走，不能按名字**（存在「书包」同名挂两个父组的多分组商品，22 个）。SKU 映射按 `skuSpecValueList` 规格值签名匹配，780/780 零失配。

### 源清单冻结（09 #31 的教训直接焊进脚本）

批量前把 512 个 goodsId 冻结成基线清单，脚本只处理清单内的，且**滤掉名字已带后缀的**——不会再造出「X（兑换）（兑换）」。

## 二、作业②积分商城整体替换：加 → 验 → 删，分组直传

### 链路

```text
① queryPointGoodsDetailForManagement(goodsId)   读原条目每 SKU 兑换值
② addPointGoods(复制体, classifyId=原积分分组)    加新条目（classifyId 直传即归位！）
③ 回读验证：兑换值/priceType/限兑/分组           五项全 PASS 才继续
④ deletePointGoods(goodsIdList:[原条目])         删原条目
```

### 三个接口的实测入参（docs/16 的补充与修正）

| 接口 | body 要点 | 坑 |
|---|---|---|
| `addPointGoods` | `classifyId` **直传目标积分分组即生效**（docs/16 只写了 0+moveGoodsToClassify 的老路，直传省一步）；`skuList[]{skuId, editChangeNum, point, pointPrice, isPoint}` | skuId 用商品的 skuList[].skuId |
| `deletePointGoods` | `goodsIdList: [...]`（数组） | UI 弹窗按钮是「**移除**」不是「确定」 |
| `updatePointGoods` | `skuList` **整体覆盖**，只收 5 字段；顶层带 `classifyId` + 强制带 `goodsLimitNum` | 不带 editChangeNum/goodsLimitNum 会被重置（docs/15 #11） |

### 兑换值保留口径

- 纯豆 `priceType=2`（现金填 0）/ 组合购 `priceType=3`，逐条保留；
- 每 SKU 的 point/pointPrice/editChangeNum 原样；
- 可兑库存按原配置额、每人限兑按原值。

## 三、两个事故复盘（都是自伤，已止损零净损失）

### 事故 1：取证脚本 abort 失效 → 误删 2 条原积分商品

`request.abort()` **在 playwright-core 里不存在**（那是 puppeteer 的 API）。52b 取证脚本调用它直接 TypeError，请求穿透落库。**拦截必须走 `page.route()` 层 `route.abort()`**（route 对象才有 abort）。route 层拦截在 53 重做后 100% 有效。

止损：删除目标本就是要清空的条目，删除前已留档完整配置（52d），重建进复制体，无净损失。

### 事故 2：editQuantity ≠ 可兑数量 → 345 条配额写错

**同一语义三个字段名都不一样**：

| 字段 | 语义 | 用途 |
|---|---|---|
| `availableChangeNum` | 可兑数量 | **读** |
| `editChangeNum` | 可兑数量 | **写** |
| `editQuantity` | 物理库存回显 | 别碰 |

计划表按 `editQuantity ?? availableChangeNum` 取值，把物理库存（如 200）当配额写入。独立复核的聚合对账抓出 345 条偏差。

**修复口径**（原聚合是剩余量）：`每SKU配置额 = (goodsAvailableNum + goodsAlreadySoldNum) / n`。全 400 条配置额均匀分布 999/9999，公式对 399/400 整除成立（剩 1 条是用户改规格的重建特例）。`updatePointGoods` 整单覆盖修复 345/345。

**通用教训**：读写字段名不一致时，用「列表聚合值 = Σ SKU 明细值」的加总关系反推验证取值对不对，别信单字段名字。

## 四、每步验证口径（两作业共用）

1. **目标变了**：新条目/复制体逐字段回读（不只是 errcode:0）。
2. **连带没被冲**：兑换值/价格/限兑在写操作前后 diff。
3. **非目标没动**：全量快照 diff，STATIC 字段零变化。
4. **具体 ID 存在性**：不看 totalCount（会漂），看目标 id 在不在列表里。
5. **聚合对账**：分组条数守恒（193/80/55/36/28/8）、库存 Σ 守恒。

## 五、下次 checklist

1. 复制类操作先取证「是接口还是前端跳转」（拦 UI 保存请求看 ep）。
2. 改写型批量：拦截保存 payload → **只改目标字段** → 放行，别重建表单。
3. 多分组/同名实体的映射一律按 id，别按名字。
4. 积分商城：加品时 classifyId 直传归位；删除按钮文案是「移除」。
5. 配额类字段先做「聚合 = Σ SKU」的口径验证再批量。
6. 拦截 abort 用 `page.route()`，别用 request 对象。

---

## 六、一句话记住

> **复制是「预填表单+保存」，改组是「改写 payload 两个字段」；积分替换是「加→验→删」，classifyId 直传归位。
> 读写字段名可能三个都不一样——用聚合加总关系反推，别信字段名。**
