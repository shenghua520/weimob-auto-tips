## 一、名词与入口对齐（第一步就要做，别猜）

后台里「兑换商城」就是**积分商城**，不是独立模块：

```
商城 > 经营工具 > 营销工具 > 商品管理-积分商品列表
https://master.weimob.com/bos/products/ecGoodsmanage/<BOS_ID>/<KEY>/goods/pointsMall/index
```

**四套「分组」不要混**（本次踩过语义歧义）：

| 名称 | 查询接口 | 层级 | 本次用途 |
|---|---|---|---|
| **商品分组**（在售商品列表） | `mall/goods/classify/queryAllClassifyListForManagement` | 两层：一级 9 / 二级 107 | ✅ **本次排序基准** |

### 写接口是怎么挖出来的（可复用手法）

不要靠猜接口名 / 扫 JS 字符串（本次扫了没抓到）。**走真实 UI，在网络层拦截写请求**：

1. 打开积分商品列表页，点「排序」列的铅笔图标 → 出现 `修改排序` 弹窗；
2. 弹窗原文： **「展示排序顺序为倒叙，数字越大越靠前」** —— 这一句决定了 `sort` 的分配方向；
3. `page.route('**/api3/**')` 把写请求 `route.abort()` 并记下 URL / body，**线上零改动**；
4. 点弹窗「确定」，抓到请求。注意输入框不在单元格里，是挂在 body 层的 `.klein-modal-footer` 弹窗。

```jsonc
// POST /api3/mall/point/goods/updatePointGoodsSort
{
  "basicInfo": { /* 从本模块页面 XHR 抄，见 13 章 */ },
  "solutionType": 2,
  "goodsId": 161456314100397,
  "pointClassifyId": 59584100397,
  "sort": 10000,
  "i18n": { "language": "zh-CN", "timezone": 8 },
  "extendInfo": { "refer": "/bos/products/ecGoodsmanage/<BOS_ID>/<KEY>/goods/pointsMall/index", "source": 80 }
}
```

> `basicInfo` 必须用**积分商城页面自己发出的**那份，别跨模块照抄（[09-#16](09-踩坑与事故复盘.md)）。

## 三、字段与排序机制

| 结论 | 依据 |
|---|---|
| `sort` **数字越大越靠前** | 弹窗文案「展示排序顺序为倒叙，数字越大越靠前」 |
| 积分商品 `sort` 与在售商品 `sort` **是两套独立字段** | 393 个可匹配商品，两侧 `sort` **全部不同**；改积分排序不会连带改在售商品列表 |
| 积分价看 `minPoint` / `maxPoint` | `minPointPrice` / `maxPointPrice` 实测为 0 |
| 分组在 `pointClassifyInfo.{pointClassifyId,name}` | 写接口要回传 `pointClassifyId` |
| `goodsStock` 是**对象**不是数字 | CSV 直接写会变 `[object Object]`，取 `goodsStock.goodsStockNum` |
| 积分商品 `sort` 值域 | 实测 1000~10000，**393 个值全不重复、无缺失** |

### 怎么判断「当前是不是按价格从低到高」

按 `sort` 降序还原展示顺序，再看相邻两条的 `minPoint` 是否非递减：

```
实测 393 条：281 / 392 = 71.7% 满足非递减；sort 有 29 处跳变，最大 8490
→ 结论：只是「大致像价格升序」，混着分组和手工调整，不是纯价格序
```

接口返回顺序 ≠ `sort` 顺序，导出表格时**同时给「按排序名次」和「接口原始序号」**两列。

## 四、本次重排规则

```
第一优先级：在售商品分组树里「二级分组」的既有顺序
            （一级 sort 降序，组内二级 sort 降序）
第二优先级：组内积分价 minPoint 升序
稳定兜底  ：接口原始顺序（并列时不乱跳）
```

**`sort` 值域最小化**：不新造数值，直接复用现有 393 个 `sort` 值的降序集合，按目标名次依次分配。
好处是值域、间隔、去重性完全不变，也天然可回滚。

```js
const sortPool = goods.map(p => Number(p.sort)).sort((a, b) => b - a);
const plan = ranked.map((x, n) => ({ ...x, newSort: sortPool[n] })); // 第 1 名拿最大 sort
```

393 条里 **391 条需写，2 条本来就在目标名次 → 不写**。
要重排顺序，改动绝大多数商品的 `sort` 是必然的；「最小化」落在 **只改 `sort` 一个字段** 上。

## 五、安全写入流程（本次全流程跑通）

| 步 | 动作 | 本次结果 |
|---|---|---|
| 0 | 只读导出 + 全量基线快照（JSON/CSV/MD，带时间戳） | 393 条积分商品 + 396 条在售商品 + 116 分组树节点 |
| 1 | `--plan` 干跑出计划表 | 391 需改 / **0 未匹配分组** |
| 2 | `--test` 小范围 12 条（第一个二级分组「铅笔」）→ 全量验收 → **自动回滚** | 12/12，静态差异 0，误改 0，在售 `sort` 变化 0 |
| 3 | 写前**即时**快照 + 回滚文件**写入前落盘**并回读校验 | 落盘成功 |
| 4 | `--apply` 全量写入（每 300ms 一条，失败 >3 即中止） | **391/391 成功，失败 0** |


## 六、验收字段要分层（本次最重要的一条经验）

线上是**正在被使用的生产环境**，验收窗口内会真实发生兑换。本次测试期间就出现：

```
goodsStock.goodsStockNum  300 → 299
frozenQuantity              0 →   1
goodsAvailableNum        9999 → 9998
goodsAlreadySoldNum         0 →   1
```

该商品**不在 12 条测试范围内**，脚本也只写 `sort` → 判定为业务自然波动。
一开始当成「回滚未完全」误报，后来把字段拆成两组：

| 组 | 字段 | 处理 |
|---|---|---|
| `STATIC` | `minPoint` `maxPoint` `minPointPrice` `maxPointPrice` `goodsLimitNum` `isOnline` `isCanSell` `title` `defaultImageUrl` `priceType` `soldType` `goodsType` `subGoodsType` `outerGoodsCode` `pointClassifyInfo.name` | **任一变化即判失败** |
| `VOLATILE` | `goodsStock` `goodsAvailableNum` `goodsAlreadySoldNum` | **只报告、不判失败、绝不「顺手修回去」** |

> [13 章](13-批量操作铁律.md) 第三节把 `sort` 列进了「清单外不许变」的字段 —— 那是针对**改价**任务写的。
> 本次任务目标字段就是 `sort`，允许改的字段清单要**按任务重列**，不能照抄上一份。

**「不该改的别改」包括：不要把别人（真实交易）造成的变化当成自己的 bug 去修复。**

## 七、回滚文件规范

```jsonc
{
  "createdAt": "2026-11-09T07:47:13.000Z",
  "baseline": "重排前基线_积分商品_<ts>.json",
  "mode": "apply",
  "count": 391,
  "items": [
    { "goodsId": 161456314100397, "pointClassifyId": 59584100397,
      "oldSort": 9890, "newSort": 10000 }
  ]
}
```

三条硬规矩：

1. **写入之前**落盘，并且落盘后立刻回读校验条目数 —— 中途崩溃 / 验收误判也要有恢复依据；
2. `items` 只记**本次真正会被写入**的条目（`test`=12 / `apply`=391），回滚时不碰任何范围外商品；
3. **schema 全局唯一**：`--rollback` 与写入侧用同一结构（可兼容旧版纯数组，但不要再覆写第二种格式）。
   本次就踩过「写入前写对象、rollback 按数组读、验收通过又覆写成数组」的不一致 —— 批量前必须修掉。

```bash
node scripts/41-resort-points-by-classify.js --rollback-file=重排回滚_<ts>.json
```

## 八、本次新增踩坑（接 [09 章](09-踩坑与事故复盘.md) 的 20 条之后）

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 21 | **白名单式路由守卫误伤只读初始化** | 把 `user/current`、`conditionQueryAndReplaceDomain` 等页面初始化 POST 也拦掉，导致查询根本发不出来、误报「未捕获到接口」 | 守卫改**黑名单**：只 abort 明确写动作，页面初始化只读 POST 一律放行；唯一放行的写接口写进 `ALLOW_WRITE` |
| 22 | **弹窗不在单元格里** | 排序编辑输入框在 body 层的 `.klein-modal-footer`，在 `<td>` 里找不到 | 扫全页新增可见 `input` / modal，点弹窗「确定」，不要只按 Enter |
| 23 | **虚拟滚动测量行** | 首行是 `height:0;padding:0` 的测量行，点它没反应 | 跳过零高度行，定位第一个真实数据行 |
| 24 | **分组名自带 `/`** | `修正带/液`、`牙膏/牙刷`、`绘本/图画书` 被 `split('/')` 拆坏，误判「未匹配分组」 | 不要拼接后按 `/` 拆；每个积分商品恰好一个二级分组，直接取 `names[0]` 用 `Map` 精确匹配 |
| 25 | **`pageSize` 铁律不可跨接口套用** | 在售商品列表 ≤20；积分商城查询 **50 可用** | 每个接口单独实测上限，别把一条结论套到所有域 |
| 26 | **环境变量不跨命令保留** | 漏带 `CHROME_PATH` 时，playwright-core 1.65 去找不存在的 `chromium_headless_shell-1254` 直接启动失败 | 凭据 / `executablePath` 每次运行都带全；或落 `config.local.js`（已在 `.gitignore`） |
| 27 | **并发业务写入被当成脚本事故** | 库存 / 已兑数在验收窗口内变化，误报「回滚未完全」 | 字段分 `STATIC` / `VOLATILE`（见第六节） |
| 28 | **回滚文件 schema 前后不一致** | 写入前写对象、回滚按数组读、验收通过又覆写成数组；中途失败时 `--rollback` 会读不出来 | 单一 schema + 写入前落盘 + 落盘校验，见第七节 |

## 十、一句话记住

> **分组口径先问清哪一套，写接口靠拦 UI 不靠猜；**
> **sort 值域复用不新造，写前快照和回滚先落盘；**
> **小样全绿才批量，验收分静态与自然波动；**
> **别人的交易不是你的 bug，别顺手改回去；**
> **收尾用另一个脚本重新登录再核一遍。**
