# SOP · 一次线上批量作业的标准流程

> 这份是**总纲**：按顺序说明「该干什么、每步产出什么、什么算过关」。
> 细节不在这里——接口细节看分册，动作清单看 [13 · 批量操作铁律](13-批量操作铁律.md)，事故案例看 [09 · 踩坑与事故复盘](09-踩坑与事故复盘.md)。
> 本章的地位：**开新任务时先读本章定框架，动手前再读 13 章过清单。**

---

## 为什么要有这份总纲

2026-11-11 那次作业（19 商品 / 39 SKU 上架 + 库存 + 积分商城）单看每一步都"会做"，但因为跳步，多花了数小时：

| 当时跳过的那一步 | 代价 |
|---|---|
| 没先查自己的经验库就动手 | 库存连错三轮、异步任务空转等了 33 分钟 |
| 没列工作条目就开始改 | 素材迁移到新分组后源分组没删，事后返工 |
| 没做小样就往全量推 | 批量改价前没发现字段口径问题（读写字段名不同） |
| 没做归因 review | 产出「铅笔 0 个商品」「9 个价格异常」两个假警报，白排查 |
| 纠错动作本身没按流程 | 入库单误填 `defectiveQty:999` → 残次 999 → 报废冲减被组件抬成 1 → 实物 998 → 再补 1 个 |

**共性根因一句话：遇阻先猜，不先取证据；批量前没做单点闭环。**

```text
                   ▼
            ④小范围测试（1 个 → 回读 → 回滚）

                   ▼
            ⑦总结沉淀（台账 + 复盘 + 回写本仓库）
```

## ① 取证与备份（全程只读）

**做什么**

- 用 GET / 查询接口把**整个目标范围**的完整状态拉下来，落盘 `backup/<对象>_<ISO时间戳>.json` + `.csv`。
- 同时记一份「基线表」：总数、ID 列表、关键字段分布。后面所有"有没有多改/少改"的判断都靠它。
- 读配置**一律用 GET 或查询接口**，禁止用空 body 的 POST 去"读"——很多后台的空 POST 会触发重置。

**产出物**：快照文件（带时间戳）+ 基线表（条数 / ID 区间 / 字段分布）

**过关标准**

- 快照条数 == 列表接口的 `totalCount`（分页要全量，别只拉前几页）。
- 覆盖的是"整个目标范围"，不是"我要改的那几项"。范围外对象也要在快照里，否则后面无法证明"没动它们"。

**反例**：`09-#15` 只拉了要改的那批做快照 → 改动扩散到范围外却查不出来。

## ② 分析与工作条目（想清楚再动手）

**做什么**：把任务拆成一行一个可验证单元，写成 plan 表。

| 序号 | 对象 | 现状 | 目标 | 依据 | 风险 | 验收方式 |
|---|---|---|---|---|---|---|
| 1 | goodsId 161734...397 | 6.24 元 + 32 豆 | 6.3 元 + 32 豆 | 规则「二舍三入」 | 进位后合计超售价 0.1 | 逐 SKU 回读比对 |

**产出物**：`plan.json` / plan 表 + 一份「**待确认清单**」

**过关标准**

- 每一行都能回答"凭什么这么改"（依据列不许空）。
- 规则有歧义（金额边界、区间开闭、单位换算）**先跑真实数据样例问清楚**，不要按理解硬套。
- 想不明白的、需要业务决策的，**单独列进待确认清单**，不要夹在计划里偷偷执行。

**反例**：规则里「二舍三入」被当成四舍五入，2 条价格错了 0.1；「3 元归低档还是高档」问了三轮才定。

## ③ 最小改动设计

**做什么**

- 只动点名范围内的对象和字段。范围外发现的问题 → **只报告，不动手**。
- 回写时**显式重建**要改的字段，不要用 `...旧快照` 展开（陈旧快照会把别人的改动盖回去）。
- 复合写入接口要连带把"必须保留的字段"也显式带上，否则会被整体覆盖/重置（例：`updatePointGoods` 不带 `editChangeNum` 会把可兑数量清回 0）。
- 删值传 `null`，不传 `0` / `''`（`0` 是真实值，`null` 才是"没有"）。

**产出物**：请求体构造代码 + 一张「允许改动清单」

**过关标准**

- 请求体里出现的字段，逐个能说出"为什么要带它"。
- 「允许改动清单」写死了：验收时清单外的字段**必须零变化**。清单按任务重列，不照抄上一份。

---

## ④ 小范围测试（1 个，闭环）

**做什么**：改 **1 条**（最多一小批 5~12 条）→ 回读 → 确认三件事 → **自动回滚**。

三件事：① 目标字段真的变了；② 连带字段没被冲掉；③ 非目标字段一个没动。

**产出物**：小样回执（改前 / 改后 / 连带字段 / 回滚结果）

**过关标准**

- 回读只看**后台接口的返回值**，不看前台页面（前台有数据层缓存，`09-#19`）。
- 样本要挑**边界型**（金额卡在分档线、SKU 最多的、字段会联动的），不是挑最顺手的那个。
- 不过就回 ③ 改设计。**不要"多试几个看看会不会好"**——那是猜，不是测。

**反例**：受控组件用 JS 直接改 `value`，视觉上有值、提交是空；`itemSkuIdList` 传字符串静默失败，连试三轮才想到查根因。

## ⑤ 大范围批量

**做什么**

- 分批：单批 ≤ 50（保守 20~30），批间 `sleep`。
- 每批落日志：成功 / 失败 / 重试 / 目标 ID。
- 失败数超阈值**立即中止**，不"跑完一起看"。
- 异步任务（返回 `result:true` + `taskId`）必须**回读确认落账**，不能把"提交成功"当"生效"。

**产出物**：执行日志 + 逐批回执 + 失败清单

**过关标准**

- 提交数 == 计划数；失败清单为空，或每条都有补救记录。
- 回滚文件必须在**写入前**落盘，并回读校验条目数。

## ⑥ 多次 review（至少三轮，角度必须不同）

| 轮次 | 视角 | 查什么 | 典型产出 |
|---|---|---|---|
| **R1 样本级** | 业务合理性 | 抽 3~5 条看数值合不合理（涨幅 >50%、价格倒挂、豆数不是整数…） | 单列给人看的异常表 |
| **R2 全量级** | 完整性 | **不带任何过滤条件**的全量扫描；目标字段 100% 合规；字段分 `STATIC`（变即失败）/ `VOLATILE`（只报告不判失败） | 合规率 + 非目标字段 diff 结果 |
| **R3 归因级** | 归属 | 这次动的到底是不是我改的？时间窗 + 主键区间 + **具体 ID 存在性** 三路交叉 | 「我方 N 个 / 他人 M 个」的分账 |
| **独立路径** | 防自证 | 另起只读脚本、重新登录回读，不复用写入脚本的运行时结果 | 第二条独立证据 |

**归因的三个坑**

- **数量会漂**：分页 `totalCount` 会因为别人同时操作而上下浮 2~3 条，别拿总数当铁证，用**具体 ID 是否存在**。
- **时间要对齐时区**：素材 `createTime` 是 UTC，比对要 +8。
- **列表接口不一定是全量**：字段缺失导致「0 个商品」这种假警报，先确认接口到底返不返回这个字段（例：商品列表不返回分组信息，判分组必须查详情）。

**过关标准**：四项齐全——目标合规 / 非目标未变 / 数量对得上 / 抽样合理。

## ⑦ 总结与沉淀（做完必须写）

**三份东西**

1. **工作点台账**：这次做了哪几件事，每件事的证据与结果（一条一行，可追溯）。
2. **失败复盘**：现象 → 根因 → 解法 → **下次怎么防**。成功的不写成长篇，失败的一条都不能省。
3. **回写本仓库**（按内容归位，不要新建大杂烩）：
   - 新接口 / 新参数 → 对应模块分册（`03`~`07`、`自查-01`）
   - 新坑 → [09 · 踩坑与事故复盘](09-踩坑与事故复盘.md)（连续编号）
   - 新动作要求 → [13 · 批量操作铁律](13-批量操作铁律.md)
   - 流程本身变了 → **本章**

**过关标准**：下次做同类任务，只读仓库就能复现整个过程，不需要问人。

---

## 三句话总结

1. **能查接口就别点页面；能回读就别信返回值；能先备份就别急着改。**
2. **小样不过不上量；全量验完才算完；范围外的只报告不动手。**
3. **顺序错了回不去**（库存清零必须早于删商品、分组迁移要先建后删），所以计划阶段就要把顺序画出来。

## 快速自检（动手前逐条打勾）

```text
[ ] 目标范围写清楚了？范围外的问题已列入"只报告"清单？
[ ] 全量快照落盘了？条数 == totalCount？
[ ] plan 表每行都有"依据"？待确认项单独列出、没有夹带执行？
[ ] 允许改动清单写死了？清单外字段零变化有办法验证？
[ ] 小样跑过并回滚过？回读用的是后台接口值？
[ ] 分批大小 / 失败阈值 / 异步任务回读点 都定了？
[ ] 三轮 review 的执行人和脚本都准备好（含一条独立路径）？
[ ] 台账 / 复盘的落点准备好了？
```
